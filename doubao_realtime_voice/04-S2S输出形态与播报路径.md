# 04 S2S 输出形态与播报路径

## 一、结论先行

**真正的 S2S（端到端语音大模型）输出的不是纯文本，也不是现成的音频波形，而是"离散的语音 token（audio tokens）"**，需要再经过一个**声码器（Vocoder）**解码成可播放的 PCM 波形。

所以流程不是：

```
❌ S2S → 文本 → TTS → 音频
```

而是：

```
✅ S2S → audio tokens → Vocoder → PCM波形 → 扬声器
```

**不再需要传统意义的 TTS，但需要 Vocoder。**

---

## 二、三种实现范式对比

### 范式1：传统三段式（Cascade / 伪 S2S）

```
语音 ─► ASR ─► 文本 ─► LLM ─► 文本 ─► TTS ─► 音频
```

- **输出是纯文本**，依赖独立 TTS 合成
- 延迟高（各环节串联 1.5~2s）
- 丢失语气、情感、停顿
- 早期"豆包语音"、车机一代方案基本都是这个

### 范式2：半端到端（Text + Speech 双输出头）

```
语音 ─► Audio Encoder ─► LLM ─► ┬─► 文本token (给字幕)
                                 └─► 音频token ─► Vocoder ─► 波形
```

- 模型**同时**输出文本和音频 token
- 文本用于字幕/日志/工具调用
- 音频 token 直出，**不经过 TTS**
- 代表：GPT-4o Realtime、Moshi、豆包实时语音大模型

### 范式3：纯端到端（Speech-only）

```
语音 ─► LLM ─► 音频token ─► Vocoder ─► 波形
```

- 完全不产生文本，内部直接在语音空间推理
- 学术前沿（如 SpeechGPT、AudioPaLM 早期版本）
- 产品上少见，因为失去了可观测性、不好接 tool call

**豆包实时语音大模型大概率是范式 2**，因为还要接字幕、工具调用、可解释。

---

## 三、Audio Token 到底是什么

不是 MP3、不是 PCM，是**离散化的语音表征**，常见编码器：

| 编码器 | 特点 | 码率 |
|---|---|---|
| SoundStream | Google 早期，8 层残差量化 | ~6 kbps |
| EnCodec | Meta，开源主流 | ~6 kbps |
| HuBERT / WavLM units | 语义为主，音色信息少 | ~1 kbps |
| Mimi (Moshi) | 专为实时对话优化 | ~1.1 kbps |

每个 audio token 代表 **20~80ms 的一小段语音**，一秒语音 ≈ 50 个 token。
LLM 预测下一个 audio token，就像预测下一个文字 token 一样。

---

## 四、Vocoder 和传统 TTS 的区别

### 传统 TTS（两阶段）

```
文本 ─► 声学模型(Tacotron/FastSpeech) ─► 梅尔频谱 ─► 声码器(HiFi-GAN) ─► 波形
       ↑ 需要"文本→语音"的对齐建模          ↑ 只负责频谱→波形
```

### S2S 的 Vocoder（一阶段）

```
audio tokens ─► Vocoder/Decoder ─► 波形
             ↑ 因为LLM已经出的是语音token，直接解码即可
```

**区别**：S2S 的 Vocoder 不需要理解"文本怎么读"，只负责把离散语音 token 还原成连续波形，职责更纯粹、延迟更低。

---

## 五、为什么这种方式更好

| 对比项 | 传统 ASR+LLM+TTS | S2S+Vocoder |
|---|---|---|
| 首包延迟 | 1.5~2s | 300~600ms |
| 情感/语气 | 丢失（文本中间态） | 保留（音频token直通） |
| 笑声/叹气/语气词 | 不支持 | 原生支持 |
| 打断响应 | 慢（要等TTS缓冲） | 快（边推边播可中断） |
| 多语言切换 | 需切换TTS引擎 | 同一个模型搞定 |
| 工程复杂度 | 三个模型串联 | 一个模型+解码器 |

## 六、回到车控场景

`帮我打开空调并且调节座椅靠背` 这个例子里：

```
S2S 输出的 token 流实际上是：

<|audio|>a₁ a₂ a₃ ... a₂₀<|/audio|>         ← "好的，马上为您"的音频token
<|tool_call|>{hvac.turn_on}<|/tool_call|>
<|tool_call|>{seat.adjust,missing:angle}<|/tool_call|>
<|audio|>a₂₁ a₂₂ ... a₆₀<|/audio|>          ← "打开空调，座椅靠背..."的音频token

解码器分流：
  audio tokens  ─► Vocoder ─► 波形 ─► 扬声器 (流式，每20个token出一段波形)
  tool_call tokens ─► Tool Executor ─► 车控总线
```

**没有独立的 TTS 步骤**，音频 token 到波形是轻量的声码器一步到位，延迟极低（<50ms）。

---

## 七、有没有"兜底的 TTS"

有，通常作为**降级方案**：

```
主路径：S2S → audio tokens → Vocoder → 波形          (正常)
降级1：S2S → 只输出文本 token → 外接TTS → 波形       (Vocoder故障)
降级2：ASR → 文本LLM → TTS → 波形                   (S2S模型不可用)
```

生产环境会同时保留传统 TTS 作为兜底，但 99% 流量走 S2S+Vocoder。

---

## 一句话总结

S2S 输出的是**离散音频 token**，经过轻量 Vocoder 直接解码成波形，**不需要传统 TTS**；文本只作为副产物用于字幕和工具调用。这也是为什么 S2S 方案的首字延迟能压到 500ms 以内、并且能保留情感和语气。
