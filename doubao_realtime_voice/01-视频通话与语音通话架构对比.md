# 01 视频通话与语音通话架构对比

## 结论先行

**大概率是"一套核心 + 多模态分支"的统一架构**，而不是两套独立系统。核心对话引擎（LLM、对话管理、工具调用、记忆）是共享的，差异主要在**输入感知层**和**实时传输层**。

---

## 一、为什么是"一套"而不是两套

从产品迭代路径看，豆包先有语音通话，后加视频通话。如果做两套，维护成本、对话一致性、功能对齐都会是灾难。合理的演进方式是：

```
语音通话架构 = ASR + LLM + TTS + 实时流
视频通话架构 = 语音通话架构 + 视觉感知分支（VLM / 视频帧理解）
```

视频通话本质上是**在语音通话链路上叠加了一路"视觉上下文"**。

---

## 二、推测的整体架构

```
                    ┌──────────────┐
  麦克风 ──► ASR ──►│              │
                    │              │
  摄像头 ──► 视觉编码器/VLM ──────►│   统一对话引擎    │──► TTS ──► 扬声器
             (帧采样/关键帧)       │  (LLM + 记忆 +   │
                                   │   工具调用 +     │──► 字幕/UI
  VAD / 打断检测 ────────────────►│   对话状态)      │
                                   └──────────────┘
                           ▲
                           │
                    WebRTC / RTC 双向实时流
```

### 关键点

1. **实时传输层**：统一用 RTC（火山引擎自家的 RTC SDK），音频是必选轨道，视频是可选轨道。
2. **感知层分叉**：
   - 音频路：流式 ASR（可能是端到端 Speech-to-Speech，省掉 ASR 显式中间态）
   - 视频路：不会每帧都过 VLM（成本爆炸），而是**关键帧采样 + 事件驱动**（用户提问时抓最近 1~3 帧，或场景变化时抓帧）
3. **对话引擎层完全共享**：同一个多模态 LLM（豆包视觉理解模型），输入是 `[历史对话, 音频文本, 视觉token]` 的序列。
4. **输出层共享**：TTS、打断、情感韵律都一套。

---

## 三、两个核心工程难点

### 1. 视频帧的"何时送、送几张"

全量送帧 = 延迟+成本双杀。合理策略是：

- 用户开始说话时，**只取说话起始时刻前后的 1~2 张关键帧**
- 配合轻量视觉模型做"画面是否有变化"的门控
- 需要"持续观察"的场景（比如用户说"你看我这样对不对"）才提高采样率

### 2. 端到端延迟预算

语音通话首包延迟目标通常 < 800ms，视频通话加了视觉理解后，要么视觉分支**并行**于 ASR（不阻塞），要么用**小而快的视觉编码器**先出 token、大 VLM 按需调用。

---

## 四、为什么不是两套

- 对话记忆、人设、工具调用（订餐、查天气等）必须一致，否则切换模式后"像换了个人"
- 豆包端上的 Speech-to-Speech 语音大模型 + 视觉理解模型，在服务侧本来就是可组合的模块
- 火山 RTC 原生支持音视频一体，没必要拆

---

## 一句话总结

一套以多模态 LLM 为核心的统一对话引擎，语音通话是"只开音频轨"的子集，视频通话是"音频+按需视觉帧"的超集。
