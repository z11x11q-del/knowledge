## 二、各层关键细节

### 1. 接入层（RTC）

| 要素 | 设计 |
|---|---|
| 协议 | WebRTC (UDP/SRTP)，车机/弱网场景降级 QUIC |
| 音频编码 | Opus 16kHz 单声道，20ms 帧 |
| 视频编码 | H.264/H.265，720p @ 15fps，关键帧按需抽取 |
| 信令 | 独立 data channel 传打断信号、字幕、状态事件 |
| 延迟预算 | 采集→服务端 ≤ 150ms |

### 2. 感知层-音频通路

**两条路线二选一**：

**方案A（传统）**：流式 ASR → 文本 → LLM

- 优点：可解释、易复用老链路
- 缺点：丢失语气/情感，延迟叠加

**方案B（端到端 S2S，豆包实时语音大模型方向）**：

- 音频直接编码成 audio tokens 喂给 LLM
- 保留情感、语速、犹豫、笑声
- 首包延迟可压到 ~500ms

**豆包目前应是 B 为主，A 作为降级兜底**。

### 3. 感知层-视觉通路（视频通话特有）

**核心思想：不要每帧都过模型**

```
帧采样调度器策略：
├─ 默认：低频心跳采样（1 fps 缩略图，做场景变化检测）
├─ 用户开始说话：抓取最近 2-3 关键帧送 VLM
├─ 用户明确指代("你看"/"这个")：立即抓帧 + 高分辨率
├─ 场景剧变(光线/主体变化)：主动抓帧并预编码缓存
└─ 静止画面：复用上一轮 vision tokens，不重复编码
```

**视觉编码器选型**：

- 轻量 ViT（如 SigLIP 级别）先出 patch tokens
- 重型 VLM 只在必要时启用
- vision tokens 缓存 30s，避免重复计算

### 4. 对话编排层（最复杂的一层）

**会话状态机**：

```
         ┌──────────┐
    ┌───►│LISTENING │◄─── 打断检测
    │    └────┬─────┘
    │         │ VAD结束 / 语义完整
    │         ▼
    │    ┌──────────┐
    │    │ THINKING │ (模型推理中)
    │    └────┬─────┘
    │         │ 首token到达
    │         ▼
    │    ┌──────────┐
    └────┤ SPEAKING │
         └──────────┘
```

**多模态上下文拼装**（每轮推理的输入构造）：

```
messages = [
  system_prompt,                    # 人设/规则
  ...long_term_memory_snippets,     # 向量检索的相关记忆
  ...recent_dialogue_history,       # 最近N轮
  current_user_turn = [
    <audio_tokens>...</audio>,      # 本轮音频
    <vision_tokens>...</vision>,    # 按需注入的视觉帧
  ]
]
```

**打断仲裁**（全双工关键）：

- 用户开口 → VAD 触发 → 立即暂停 TTS 播放
- 判断是"附和"（嗯、对）还是"真打断"（重新提问）
- 附和：不中断生成；真打断：丢弃当前生成，进入新轮次

### 5. 核心模型层

- **统一模型**：语音/视频共用同一个多模态 LLM，只是输入 token 类型不同
- **流式推理**：边生成边输出 token 给 TTS，不等整句
- **Tool Call 并行化**：工具调用和继续生成话术并行（"好的，我帮你查一下天气……"边说边调）

### 6. 生成层

- **流式 TTS**：首 token 到达即开始合成，首包 <300ms
- **韵律注入**：LLM 输出带 SSML 标记或情感 token，TTS 按需变调
- **字幕对齐**：TTS 产出时间戳 → 回传客户端渲染

## 三、端到端延迟预算（视频通话为例）

| 环节 | 耗时 |
|---|---|
| 采集+RTC上行 | 150ms |
| 音频编码→LLM | 100ms |
| 视觉帧编码（并行） | 150ms（不阻塞音频） |
| LLM 首 token | 300ms |
| TTS 首包 | 200ms |
| RTC 下行+播放 | 150ms |
| **首字发声总延迟** | **~900ms** |

视觉通路**并行**于音频，不叠加到主路径延迟。

---

## 四、可靠性与降级

```
视觉模型超时/过载  → 降级为纯语音通话（保留视觉token缓存）
S2S模型不可用      → 降级到 ASR+LLM+TTS 三段式
RTC弱网            → 降码率 → 降帧率 → 关视频 → 只保音频
LLM推理超时        → 兜底话术("稍等，我想想")+ 重试
```

---

## 五、为什么这样设计是合理的

1. **一套引擎**：对话一致性、记忆/人设/工具调用共享，避免语音/视频切换时"人格分裂"
2. **分支解耦**：视觉是可选增强，不拖累语音通话的既有性能
3. **流式贯穿**：从 RTC 到 ASR 到 LLM 到 TTS 全链路流式，延迟可控
4. **按需视觉**：帧采样调度器是成本控制的关键，也是豆包能把视频通话做到免费开放的前提

---

## 核心判断

豆包视频通话 = 语音通话链路 + 一条"事件驱动的视觉感知旁路" + 多模态 LLM 对输入的统一理解。架构层面是一套，工程层面视觉通路有独立的采样/编码/缓存子系统。
