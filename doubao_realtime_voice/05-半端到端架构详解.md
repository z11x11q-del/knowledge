# 05 半端到端架构详解（Text + Speech 双输出头）

## 一、核心定义

**半端到端**指模型**内部推理**是端到端的（语音直接进、语音直接出），但**输出空间**同时包含两种 token：

- **Text tokens**：文字（给字幕、工具调用、日志、记忆）
- **Audio tokens**：离散语音表征（给声码器合成波形）

两种 token 在**同一个 Transformer 的同一次前向**中交错生成，共享 KV cache、共享注意力、共享参数。

> 关键词：**"一个模型、两个头、一条序列"**

---

## 二、内部结构详解

### 2.1 整体拓扑

```
┌─────────────────────────────────────────────────────────────┐
│                       输入侧                                  │
│                                                              │
│  用户语音 ──► Audio Encoder ──► audio tokens (in)            │
│                    (EnCodec/Mimi/SpeechTokenizer)             │
│                                                              │
│  历史对话 ──► Tokenizer     ──► text tokens (in)             │
│                                                              │
│  合并为统一序列:                                               │
│  [<sys>][text_hist][<user>][audio_in][<assistant>]           │
└──────────────────────┬───────────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────────┐
│              统一 Transformer Decoder                          │
│                                                              │
│  词表 = text_vocab (~100K) ∪ audio_vocab (~4K~32K) ∪ 控制符 │
│                                                              │
│  每一步预测下一个 token，可以是:                                │
│    ├─ text token (如 "好"、"的")                              │
│    ├─ audio token (如 a_4521)                                │
│    └─ 控制 token (<tool_call>, <speech_start> 等)            │
└──────────────────────┬───────────────────────────────────────┘
                       ▼
            按 token 类型实时分流
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
  ┌──────────┐  ┌──────────┐  ┌──────────────┐
  │ 文本通道  │  │ 音频通道  │  │ 控制/工具通道  │
  │ (字幕/日志)│  │ Vocoder  │  │ Tool Executor │
  │           │  │ ↓波形    │  │               │
  └──────────┘  └──────────┘  └──────────────┘
```

### 2.2 扩展词表的关键

传统 LLM 词表只有 text token（~10万个），半端到端 LLM 把**音频编码器的码本**也加进词表：

```
词表构成：
├─ [0, 100000)       : 文本 BPE token
├─ [100000, 104096)  : audio codebook level 0 (~4K)
├─ [104096, 108192)  : audio codebook level 1 (~4K)
├─ [108192, ...)     : 更多残差层 (RVQ 多级量化)
└─ 末尾              : 特殊控制 token (<bos><eos><tool_call>...)
```

模型不需要改架构，**只是词表变大了，softmax 输出维度扩展到几十万**。

## 三、两种 Token 怎么"交错"出现

有三种常见编排方式：

### 方式 A：严格交错（Interleaved，Moshi 用法）

```
序列: t₁ a₁ a₂ t₂ a₃ a₄ t₃ a₅ a₆ ...
      文 音 音 文 音 音 文 音 音

每 2 个 audio token 后插一个 text token
```

- **强时间对齐**：text 紧跟对应音频段
- 好处：字幕和语音自然同步
- 坏处：词表设计和训练复杂

### 方式 B：分段串行（Segmented）

```
序列: <text>好的，马上为您</text>
      <audio>a₁ a₂ ... a₂₀</audio>
      <tool_call>{hvac.turn_on}</tool_call>
      <text>打开空调</text>
      <audio>a₂₁ ... a₄₀</audio>
```

- 先出一段文字，再出对应音频
- 好处：实现简单，各通道职责清晰
- 坏处：字幕可能比语音早一点出现

### 方式 C：双流并行（Parallel Streams，GPT-4o 风格）

```
文本流: ─►好─►的─►，─►马─►上 ...
音频流: ─►a₁─►a₂─►a₃─►a₄─►a₅...
        (两条流同一时间步同时预测，各用一个头)
```

- 两个独立的输出头，主干 Transformer 共享
- **延迟最低**，真正同步
- 训练需要强监督的对齐数据

豆包实时语音据推测接近**方式 C**（或 B+C 混合）。

## 四、一次前向的实际 Token 流示例

拿 `帮我打开空调并且调节座椅靠背` 举例，模型输出序列（简化）：

```
输入:
  [<sys>车机助手人设]
  [<user><audio>用户query的音频token序列</audio>]
  [<assistant>     ← 从这里开始自回归生成
  
生成:
  <speech_start>
    <text>好</text><audio>a₁a₂</audio>
    <text>的</text><audio>a₃a₄</audio>
    <text>，</text><audio>a₅</audio>
    <text>马上为您</text><audio>a₆...a₁₂</audio>
  <speech_end>
  
  <tool_call>
    {"name":"hvac.turn_on","args":{}}
  </tool_call>
  
  <tool_call>
    {"name":"seat.adjust_backrest","args":{"angle":null}}
  </tool_call>
  
  <speech_start>
    <text>打开空调</text><audio>a₁₃...a₂₀</audio>
    <text>，座椅靠背调到多少度？</text><audio>a₂₁...a₄₀</audio>
  <speech_end>
```

**关键观察**：

- Text 和 Audio 在同一个序列里，按文本片段 + 对应音频段的方式交替
- Tool call 出现时，**既不是文本也不是音频**，是独立的结构化 token 块
- 模型的自回归生成天然决定了顺序：说完"马上为您" → 派发 tool → 继续说

## 五、训练范式：怎么训出来的

### 阶段 1：语音 Tokenizer 预训练

- 独立训练 EnCodec / Mimi 等，得到 audio 的离散码本
- 冻结，作为后续阶段的编码/解码器

### 阶段 2：语音 LM 预训练

- 用大量无标注语音，纯自回归预测下一个 audio token
- 相当于"语音版的 GPT pre-train"
- 学会语音的统计规律（音素、韵律、说话人特征）

### 阶段 3：文本-语音对齐预训练

- 用 TTS 生成的 `(文本, 对齐音频)` 对，训练交错序列
- 让模型理解 text ↔ audio 的对应关系

### 阶段 4：多模态对话 SFT

- 高质量的 `(用户语音, 助手语音+text+tool_call)` 对话样本
- 加入工具调用的标注样本
- 模型学会"什么时候说话、什么时候调工具、什么时候反问"

### 阶段 5：RLHF / DPO

- 基于真实用户反馈优化：打断体验、语气自然度、工具调用准确率

## 六、半端到端 vs 纯端到端 vs 传统 cascade

| 维度 | 传统 Cascade | 纯 S2S（Speech-only） | 半端到端（本方案） |
|---|---|---|---|
| 输出 | 文本→TTS→波形 | 仅 audio tokens | audio + text + tool 混合 token |
| 首包延迟 | 1.5~2s | 300ms | 400~600ms |
| 情感保留 | 丢失 | 保留 | 保留 |
| 字幕生成 | 直接有 | 需额外 ASR 回捞 | **直接有** ✓ |
| 工具调用 | 好接 | 难接（都是语音） | **好接** ✓ |
| 可观测性 | 高 | 低 | **高** ✓ |
| 训练复杂度 | 低 | 中 | 高 |
| 工程落地 | 成熟 | 学术/小范围 | **产品主流** |

**半端到端是当前产品级实时语音的最优解**，兼顾了端到端的延迟/情感优势和 cascade 的可观测性/可接入性。

## 七、关键工程难点

### 1. Text 和 Audio 的速率不匹配

- 1 秒语音 ≈ 50 个 audio token，但对应文本可能只有 2~5 个汉字（token）
- 解决：文本 token 插入频率远低于音频，或用 padding token 对齐

### 2. KV cache 膨胀

- 一分钟对话 ≈ 3000 audio tokens + 几百文本 token，上下文压力大
- 解决：滑窗注意力、历史音频转文字后释放原始 audio tokens

### 3. 工具调用阻塞问题

- 模型边说边想调工具，但工具结果需要时间返回
- 解决：异步 tool call + 占位话术（"稍等我查一下..."）+ 结果回注时继续生成

### 4. 多说话人 / 打断

- 用户说话时，模型还在输出音频 token，需要实时停止解码
- 解决：VAD 触发中断信号，丢弃未播放的 token 队列

## 一句话总结

半端到端 = **一个 Transformer 主干 + 扩展词表（文本+音频+控制符）+ 多通道输出分流**；它保住了端到端的低延迟和情感表现，又通过同步输出文本换回了字幕、工具调用、日志、记忆这些产品必需的能力。这是目前豆包、GPT-4o 这类实时对话产品的主流底座。
