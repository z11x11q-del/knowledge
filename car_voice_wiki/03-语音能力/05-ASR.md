# ASR 自动语音识别 —— 后端工程实践

## 1. 整体定位

ASR（Automatic Speech Recognition）在车机语音链路中处于**最前置的感知层**，其输出质量直接决定后续 NLU / DM / LLM 的上限。后端视角关注的核心问题：

- **接入形态**：流式 vs 非流式，端侧 vs 云端，SDK 嵌入 vs RPC 解耦
- **时延**：首包时延、尾包时延、端到端 TTFR（Time To First Recognition）
- **准确率**：WER / SER，尤其是垂域词（车控、地名、歌曲、联系人）的识别率
- **稳定性**：弱网/断网降级、服务过载熔断、多引擎容灾
- **工程治理**：版本管理、热词更新、Badcase 闭环

---

## 2. 接入架构

### 2.1 典型链路

```
麦克风阵列（AEC/降噪/波束成形）
      │
   前端处理（端侧 DSP / NPU）
      │
   VAD 检测（端侧）
      │  音频流（PCM / Opus）
   ┌──▼──────────────────────────┐
   │   ASR 服务（云端 / 边缘）    │
   │   ┌─────────┐ ┌──────────┐ │
   │   │ 声学模型 │ │ 语言模型  │ │
   │   │  AM     │ │   LM     │ │
   │   └─────────┘ └──────────┘ │
   │        流式 Decoder         │
   └──────────────┬──────────────┘
                  │ 中间结果 / 最终结果（JSON）
              NLU / 判决层
```

### 2.2 接入形态对比

| 维度 | 端侧 SDK | 云端 RPC | 边缘节点 |
|------|---------|---------|---------|
| 时延 | 最低（< 50ms） | 网络依赖（100~300ms） | 中等 |
| 准确率 | 受端侧算力限制 | 高（大模型） | 较高 |
| 弱网可用性 | 强 | 弱 | 中 |
| 热词/模型更新 | 需 OTA | 实时 | 近实时 |
| 车机资源占用 | 高（CPU/内存） | 低 | 低 |

**实践选择**：主流方案为**端侧轻量 ASR 兜底 + 云端大模型 ASR 主路**，VAD 切帧后并发请求，取先到结果或按置信度仲裁。

## 3. 流式识别协议设计

### 3.1 为什么要流式

车机场景用户说完整句话通常 2~5s，如果等 VAD 尾点再发送，会引入额外 200~500ms 感知时延。流式 ASR 在用户说话过程中持续返回**中间结果（partial result）**，后端可以：

- 提前触发 NLU 预热
- 展示滚动字幕提升感知响应
- 结合打断检测提前打断播报

### 3.2 典型 WebSocket 协议帧设计

```
// 客户端 → ASR 服务
{
  "type": "start",
  "session_id": "uuid",
  "config": {
    "sample_rate": 16000,
    "encoding": "pcm_s16le",
    "language": "zh-CN",
    "hotwords": ["导航去", "打电话给", "播放音乐"],
    "domain": "car",
    "vad_mode": "server"   // 服务端 VAD / 客户端 VAD
  }
}

// 客户端持续发送音频包（二进制帧，160ms 一包）

// 服务端 → 客户端（流式中间结果）
{
  "type": "partial",
  "session_id": "uuid",
  "text": "导航去北",
  "stability": 0.7
}

// 服务端 → 客户端（最终结果）
{
  "type": "final",
  "session_id": "uuid",
  "text": "导航去北京西站",
  "confidence": 0.95,
  "words": [
    {"word": "导航", "start_ms": 120, "end_ms": 480, "confidence": 0.98},
    ...
  ],
  "vad_end_ms": 2340
}
```

### 3.3 分包策略

- **固定帧长**：每 160ms（2560 字节 @ 16kHz/16bit）发送一包，实现简单，适合大多数场景
- **VAD 感知分包**：检测到静音段主动发 `flush` 信号，加速服务端 Decoder 收尾
- **背压控制**：客户端维护发送队列，服务端返回 `ack` 或 `buffer_full` 时暂停发送，避免丢帧

## 4. 热词（Hotword / Biasing）工程实践

### 4.1 为什么热词是工程重点

通用 ASR 对垂域词汇识别率低，车机场景典型问题：
- 联系人姓名（"刘一鸣"识别成"刘一名"）
- 地名（"望京 SOHO"识别错）
- 歌曲 / 歌手名（长尾词汇）
- 车控指令（"开启座椅加热"中的品牌专有词）

### 4.2 热词注入方式

```
┌─────────────────────────────┐
│         热词来源             │
│  联系人 / 收藏地址 / 播放列表  │
│  车控词表 / 品牌专有词         │
└────────────┬────────────────┘
             │ 构建热词包（< 2KB JSON）
             ▼
    随 ASR 请求 Header 下发
    或通过热词预加载接口缓存
             │
             ▼
    Decoder 侧加权（Shallow Fusion）
    在解码 Beam Search 中对热词路径加分
```

### 4.3 热词权重调优

热词权重过高会导致**过触发**（把无关词识别成热词），过低则无效。工程实践：

- 权重默认值：`10~15 dB`（各厂商定义不同，需实验）
- 按词频动态调权：高频热词降权，避免过触发
- 分类隔离：联系人热词 / 地名热词 / 音乐热词分组，按上下文激活对应组
- 定期离线评测：用专项测试集验证热词召回率与误触率

## 5. 多引擎容灾与路由

### 5.1 架构设计

```
              ┌──────────────────────┐
              │     ASR 网关 / Router │
              └───┬──────────────────┘
         ┌────────┤
         │        │
    ┌────▼──┐  ┌──▼────┐  ┌──────────┐
    │ 主引擎 │  │ 备引擎 │  │ 端侧兜底  │
    │ (云A) │  │ (云B) │  │ (端侧SDK)│
    └───────┘  └───────┘  └──────────┘
```

### 5.2 路由策略

- **健康检查**：每 5s 探测一次各引擎 `/health`，RT > 500ms 或错误率 > 5% 触发降级
- **超时兜底**：云端 ASR 超过 `200ms` 未返回首包，自动切端侧引擎
- **弱网检测**：网络质量差（RTT > 300ms 或丢包 > 3%）时直接走端侧路径
- **熔断器**：采用 Hystrix 模式，连续失败 N 次后开路，半开期定期重试

### 5.3 结果仲裁

双引擎并发场景下：
- 取**先返回最终结果**的引擎输出
- 若两者均返回，取 `confidence` 较高者
- 对于关键词（如车控指令）可做交叉验证，两者均识别才下发执行

## 6. 时延优化

### 6.1 时延分解

```
用户说完 → VAD 尾点检测 → 网络传输 → ASR Decode → 返回结果
   ↑              ↑             ↑            ↑
  0ms          50~200ms      30~80ms      100~300ms
```

**TTFR 目标**：端到端 < 400ms（用户感知流畅阈值）

### 6.2 优化手段

| 优化点 | 方案 | 收益 |
|--------|------|------|
| VAD 尾点优化 | 缩短静音等待（500ms → 300ms），结合语义预判提前截断 | -100~200ms |
| 流式传输 | 边说边传，并发发包，消除"说完再发"串行等待 | -200~400ms |
| 连接复用 | WebSocket 长连接 / HTTP/2，消除 TCP + TLS 握手 | -50~100ms |
| 服务端预热 | 会话开始时预加载热词和语言模型上下文 | -30~50ms |
| 边解码边推理 | partial result 触发 NLU 预热，TTFR 提前 | 感知 -200ms |
| CDN / 就近接入 | 音频流就近上传到离车机最近的边缘节点 | -20~60ms |

## 7. 准确率提升工程实践

### 7.1 数据闭环

```
线上 ASR 结果
     │
     ▼
Badcase 挖掘
（低置信度 / 用户重说 / NLU 解析失败）
     │
     ▼
人工标注 / 自动标注（大模型辅助）
     │
     ▼
增量训练 / Fine-tune
     │
     ▼
离线评测（WER / SER / 垂域词召回率）
     │
     ▼
灰度上线 → 全量
```

### 7.2 关键指标

| 指标 | 说明 | 目标参考值 |
|------|------|----------|
| WER | 词错误率 | < 5%（安静环境）|
| SER | 句错误率 | < 15% |
| 垂域词召回率 | 热词识别召回 | > 95% |
| 热词误触率 | 非热词被识别成热词 | < 1% |
| P99 时延 | 最终结果返回时延 | < 800ms |
| 可用率 | 请求成功率 | > 99.9% |

### 7.3 噪声鲁棒性

车内噪声场景（发动机、风噪、音乐外放）对 ASR 影响显著：
- **前端降噪**：麦克风阵列波束成形 + AEC（回声消除）是基础，后端 ASR 服务不能假设输入音频已经干净
- **噪声增强训练**：在训练集中混入车内真实噪声（不同车型、不同车速）
- **信噪比估计**：服务端收到音频后估计 SNR，低 SNR 时切换噪声鲁棒性更强的模型或调整 Beam Size

## 8. 工程治理

### 8.1 版本与灰度

- ASR 模型更新采用**蓝绿发布**，流量按设备 ID hash 分流
- 模型版本号随最终结果下发，方便线上回溯
- 灰度期间同时收集新旧模型的识别结果，自动对比 WER 差异

### 8.2 监控告警

```yaml
# 关键监控项
- asr_request_total          # QPS
- asr_error_rate             # 错误率（区分超时 / 引擎错误 / 网络错误）
- asr_latency_p50/p99        # 时延分位数
- asr_final_confidence_avg   # 平均置信度（偏低时告警，可能是噪声环境增多）
- asr_hotword_hit_rate       # 热词命中率
- asr_engine_fallback_rate   # 降级到备引擎的比例
```

### 8.3 日志规范

每次 ASR 请求需记录：
- `session_id`、`device_id`、`request_id`
- 音频时长、采样率、编码格式
- 热词列表（hash，不记录明文联系人姓名，隐私合规）
- 识别结果、置信度、各词时间戳
- 引擎版本、时延（首包 / 尾包 / 端到端）
- 是否触发降级，降级原因

### 8.4 隐私合规

- 音频数据**不落盘**于车机本地，仅流式上传至云端
- 云端处理完成后音频流立即销毁，不长期存储原始音频（或获取用户授权后保留用于优化）
- 热词中的联系人姓名在传输时做本地加密或 hash，服务端只持有映射关系不持有明文

## 9. 常见问题与排查思路

| 现象 | 可能原因 | 排查方向 |
|------|---------|---------|
| 识别结果为空 / 超时 | 网络抖动、引擎过载 | 检查 error_rate 监控、网络 RTT |
| 连续说错（WER 突然升高） | 噪声环境变化、模型版本问题 | 对比新版本 WER、检查 SNR 分布 |
| 特定词总识别错 | 热词未覆盖、权重不足 | 检查热词列表、调整权重 |
| 热词过触发 | 热词权重过高、词形相似 | 降低权重、增加上下文过滤 |
| partial 结果跳变 | Decoder beam 不稳定 | 调整 stability 阈值，部分场景仅展示高稳定 partial |
| 首包时延高 | 连接未复用、服务端冷启动 | 检查长连接复用率、预热机制 |
