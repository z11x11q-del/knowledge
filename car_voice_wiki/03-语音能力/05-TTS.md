# TTS（文本转语音）工程实践

> 视角：车机语音助手后端，关注 TTS 在实际系统中的接入、调度、性能优化与可靠性保障。

---

## 1. TTS 在整体链路中的位置

```
LLM/NLG 输出文本
      │
      ▼
  文本预处理（规范化、分句）
      │
      ▼
   TTS 引擎（云端 / 端侧）
      │
      ▼
  音频流（PCM / Opus / MP3）
      │
      ▼
  车机播报（扬声器输出）
```

TTS 是整条语音交互链路中**最靠近用户感知**的环节，其延迟和音质直接决定用户体验。后端工程师的核心职责是：**降低首包延迟、保障流式稳定、处理异常降级**。

---

## 2. 关键指标定义

| 指标 | 含义 | 典型目标 |
|------|------|----------|
| **TTFF**（Time to First Frame） | 从文本送入 TTS 到收到第一帧音频的耗时 | ≤ 300ms（云端） |
| **实时率（RTF）** | 合成 1s 音频所需的计算时间，RTF < 1 表示可实时 | RTF < 0.3 |
| **端到端播报时延** | 用户说完 → 车机开始出声 | ≤ 1.2s（业界标杆） |
| **合成成功率** | 成功返回音频帧的请求比例 | ≥ 99.9% |
| **音频流断帧率** | 播放过程中出现卡顿/断帧的比例 | ≤ 0.1% |

---

## 3. 接入模式

### 3.1 云端 TTS（主路）

```
后端服务  ──gRPC/WebSocket──►  TTS 云服务
          ◄── 流式音频帧 ──────
```

- 主流协议：**gRPC 双向流** 或 **WebSocket**，支持边合成边下发。
- 音频格式：PCM 16kHz/24kHz 单声道（车机标准），部分场景用 Opus 压缩传输。
- 鉴权方式：Token + AppKey，需处理 Token 过期与自动刷新。

### 3.2 端侧 TTS（兜底 / 离线）

- 部署在车机本地，无网络依赖，延迟极低（< 50ms TTFF）。
- 音质通常弱于云端，适合：弱网降级、简短系统提示音（"好的"、"正在处理"）。
- 后端需下发**降级指令**，车机 SDK 切换到本地引擎。

### 3.3 混合策略

```
请求到达
    │
    ├─ 网络质量好 ──► 云端 TTS（高音质）
    │
    └─ 弱网 / 超时 ──► 端侧 TTS（兜底）
```

## 4. 流式合成与分句策略

### 4.1 为什么要分句

LLM 输出是流式 token，不能等全文生成完再送 TTS，否则时延无法接受。需要**边生成边切句、边切句边合成、边合成边播报**。

### 4.2 分句规则（工程实现要点）

```python
# 伪代码示意
SENTENCE_END_PATTERNS = r'[。！？…\n]|[.!?](?=\s)'

def split_streaming_text(buffer: str) -> tuple[list[str], str]:
    """
    返回：(已完整句子列表, 剩余未结束的 buffer)
    """
    sentences = []
    while True:
        match = re.search(SENTENCE_END_PATTERNS, buffer)
        if not match:
            break
        end = match.end()
        sentences.append(buffer[:end].strip())
        buffer = buffer[end:]
    return sentences, buffer
```

**注意事项：**
- 省略号 `……` 需去重，避免切出空句。
- 数字、缩写中的句点（`3.14`、`Dr.`）不能触发切句。
- 最后一句如果 LLM 流结束但无标点，需强制 flush。
- 句子长度建议控制在 **20~50 字**，过短导致合成请求频繁，过长增加 TTFF。

### 4.3 流水线并行

```
LLM 流输出:   [句1]──────[句2]──────[句3]
                │           │           │
TTS 合成:      [合成句1]  [合成句2]  [合成句3]
                    │           │           │
车机播报:           [播句1]    [播句2]    [播句3]
```

三级流水线并行，理论上播报时延 ≈ TTFF(句1) + LLM首token延迟，而不是全文合成时间。

## 5. 音频帧管理

### 5.1 帧格式约定

| 字段 | 说明 |
|------|------|
| `session_id` | 本次 TTS 请求唯一标识 |
| `seq` | 帧序号，单调递增，用于排序和检测丢帧 |
| `is_last` | 是否为最后一帧 |
| `audio_data` | 音频裸数据（PCM bytes） |
| `timestamp_ms` | 服务端生成时间戳，用于延迟监控 |

### 5.2 背压控制

- 合成速度 > 播放速度时，需在后端做**缓冲队列**，避免车机 buffer 溢出。
- 播放速度 > 合成速度时，出现**饥饿**，需上报监控并触发降级。
- 建议：每路会话维护独立的环形缓冲区，缓冲 2~3s 音频。

## 6. 打断处理

TTS 播报过程中，用户随时可能再次说话触发打断。打断链路：

```
VAD 检测到用户说话
      │
      ▼
后端收到打断信号
      │
      ├─► 立即停止向车机下发 TTS 音频帧（发送 stop 指令）
      │
      └─► 取消/丢弃当前 TTS 合成请求（不再消费后续 token）
```

**工程实现要点：**
- TTS 请求需支持**提前取消**（gRPC `cancel` / WebSocket `close`），避免浪费算力。
- 已发出但未播完的帧，车机 SDK 需在收到 stop 指令后立即清空播放队列。
- 打断后的新一轮请求需携带新的 `session_id`，防止旧帧混入。

## 7. 异常处理与降级

### 7.1 超时分级处理

```
TTS 请求发出
    │
    ├─ 300ms 内无首帧 ──► 播放"提示音"，继续等待
    │
    ├─ 800ms 内无首帧 ──► 切换端侧 TTS 兜底
    │
    └─ 端侧也失败 ──────► 静默跳过本句，播放下一句
```

### 7.2 常见错误类型

| 错误类型 | 处理策略 |
|----------|----------|
| 网络超时 | 重试（最多1次） + 降级端侧 |
| 鉴权失败（Token 过期） | 自动刷新 Token 后重试 |
| 文本超长（> 引擎限制） | 预处理截断，分多次请求 |
| 引擎内部错误（5xx） | 不重试，直接降级 |
| 特殊字符/符号导致崩溃 | 文本预处理过滤 |

### 7.3 降级话术兜底

对于 LLM 长回复，若 TTS 全部失败，不应静默无响应，需返回预设降级话术：
> "抱歉，语音播报暂时不可用，请查看屏幕显示内容。"

## 8. 文本预处理（TTS 前置规范化）

原始 LLM 输出包含大量 TTS 引擎不友好的内容，需在送入 TTS 前处理：

| 问题类型 | 示例 | 处理方式 |
|----------|------|----------|
| Markdown 格式 | `**加粗**`、`# 标题` | 剥除标记，保留文本 |
| 数字读法 | `2024` → "二零二四" vs "两千零二十四" | 按上下文判断（年份/数量） |
| 英文缩写 | `km/h`、`USB` | 转为全称或逐字母读 |
| 特殊符号 | `@`、`/`、`%` | 转义或转为中文读法 |
| 表情/Emoji | `😊` | 过滤或转为文字描述 |
| URL | `https://...` | 过滤或提示"详见链接" |
| 代码块 | ` ```python ... ``` ` | 替换为"以下是代码示例" |

## 9. 多发音人管理

车机场景通常支持多种音色（女声默认、男声、儿童音等），后端需管理：

```json
{
  "voice_config": {
    "default": "xiaomei_standard",
    "scene_overrides": {
      "navigation": "xiaomei_calm",
      "alert": "system_alert_tone",
      "child_mode": "kid_voice"
    }
  }
}
```

- 音色切换需**无缝衔接**，不能在句子中途换音色。
- 用户个性化偏好存储在用户画像服务，TTS 请求时动态读取。

## 10. 监控与可观测性

### 10.1 核心监控指标

```
tts_request_total{status="success|fail|timeout"}  # 请求量
tts_ttff_ms{p50, p95, p99}                        # 首帧延迟分布
tts_rtf{engine="cloud|local"}                     # 实时率
tts_fallback_total{reason="timeout|error|network"} # 降级量
tts_audio_gap_total                                # 音频断帧次数
```

### 10.2 链路追踪

每次 TTS 请求需携带 `trace_id`（与上游 LLM 请求同一 trace），便于：
- 端到端延迟拆解（LLM 耗时 vs TTS 耗时 vs 网络耗时）
- Badcase 回溯（哪句话合成失败或音质差）

### 10.3 告警规则建议

| 告警项 | 阈值 | 级别 |
|--------|------|------|
| TTFF P95 > 600ms | 持续 2min | P1 |
| TTS 成功率 < 99% | 持续 1min | P0 |
| 降级率 > 5% | 持续 5min | P2 |
| Token 刷新失败 | 任意一次 | P1 |

## 11. 性能优化实践

### 11.1 连接复用
- 使用 **gRPC 长连接 + 连接池**，避免每次请求建连开销（节省 50~100ms）。
- 对云端 TTS 保持 keep-alive，检测连接健康。

### 11.2 预热与缓存
- **高频固定话术缓存**：导航播报、系统提示（"好的"、"收到"）预先合成并缓存音频文件，命中缓存时 TTFF ≈ 0。
- **模型预热**：服务启动时发送 warm-up 请求，避免冷启动慢。

### 11.3 并发控制
- 单会话串行：同一 session 的句子必须按序合成，不能并发乱序。
- 跨会话并行：不同用户会话可并发，需控制总并发数防止压垮 TTS 服务。

### 11.4 音频压缩
- 车机网络带宽有限，PCM 24kHz 码率约 384kbps。
- 使用 **Opus 编码**可压缩至 32~64kbps，节省约 85% 带宽，延迟增加 < 10ms。
