# Prompt 该退环境了，未来属于 Loop Engineering

> 原文链接：<https://x.com/Khazix0918/status/2066394718519656909>
>
> 作者：Khazix（@Khazix0918）
> 提取时间：2026-06-16

---

最近，AI 行业又出现了一个有趣的新词 —— **Loop Engineering**。如果你关注 AI 这个领域，这两天应该都会刷到：推特在刷、各种社媒也在刷、群里也有蛮多人在讨论。

事情是这样的。Peter Steinberger 发了一条推，非常简短，但直接就爆了：

> "You shouldn't be prompting coding agents anymore. You should be designing loops that prompt your agents."

翻译过来意思就是：你不再需要为编码智能体编写提示词了，你应该设计循环来提示你的 Agent。

而在这之前几天，Claude Code 的创始人 Boris Cherny 在一个开发者大会上说了差不多的话：

> "I don't prompt Claude anymore. I have loops running that prompt Claude and figuring out what to do. My job is to write loops."

也就是，**写 loop**。

这两个人说了同一件事。然后 Google 的 Addy Osmani 紧接着发了一篇长文，把 Loop Engineering 这个概念正式梳理了出来。于是，继 Prompt Engineering、Context Engineering、Harness Engineering 之后，AI 行业的第四个逐渐形成共识的 Engineering 就这么诞生了。

我自己其实是个特别不喜欢造新词的人，但很多时候造词这事得分两种情况：有一种是为了炒概念（比如 xxx 4.0）；有的时候真的只是行业太快，人们需要一个精准的表达来帮助自己表达而已。Loop Engineering 我觉得就是后一种。

而且这个东西跟我自己一直使用 Agent 的方法、一直在鼓励大家做的事，是高度吻合的。如果你看过我之前写的 Harness Engineering 文章，大概能理解一些我的感觉 —— 那篇文章里我聊了从 Prompt 到 Context 到 Harness 的三次跃迁，聊了马具和缰绳的比喻，聊了约束先行。而 Loop Engineering 其实就是在 Harness 之上又往上走了一层：把一个套马的缰绳变成了全自动工业流水线。很有《文明》里时代进化的感觉。

## 一个具体的例子

以前用 Claude Code 写代码，流程大概是这样的：你给它一个任务，它写完了，你看一眼，觉得不太对，再给它提修改意见，它改完了，你再看、再提。整个过程是坐在设备前的，一轮一轮的，你说一句它回一句——**你就是那个驱动整个循环的发动机**。

而 Boris Cherny 的工作方式是：他写一个 loop，比如 `/loop babysit all my PRs`，自动修 CI 问题，有新评论就派子 Agent 去处理。然后 Claude Code 就开始自己跑了，自动去看他 GitHub 上所有的 PR，哪些 CI 挂了就自己修，哪些 review 有新评论就自动派一个独立的工作树 Agent 去改代码。

他还把其他一些 loop 挂到定时任务上，每天晚上自动启动去干这事。**晚上睡觉的时候，甚至有时候会有几千个 Agent 在同时工作**。他说，2026 年他再也没有手写过一行代码。

这就是 loop：定好目标，然后全自动流程化，你完全不需要在电脑前，甚至不需要看手机。醒来的时候，代码已经改好了，测试也跑过了，PR 已经提上去了。

> 你不是给 Agent 写了一段 Prompt 完成某个单次任务，而是你自己设计了一个目标，这个目标使用 loop 的方式帮你提示 Agent。你定义目标、定义验证条件、定义失败怎么处理，然后就可以放手了——交给系统。

## Loop 的五个组件

Addy Osmani 在他那篇长文里，把一个完整的 loop 拆成了五个组件：

### 1. 定时任务（Trigger）
整个 loop 的心跳。不管是定时跑还是事件触发，都得有一个东西能自动启动循环。

- `/loop` 命令按间隔自动执行
- cron 定时调度
- Hook 在 Agent 生命周期的特定节点自动触发（比如每次改完文件自动跑一遍 lint）
- 或者直接丢到 GitHub Actions 里，关上电脑它也在跑

**没有定时任务的 Agent，每次都得手动去踢一脚才会动，那就不是 loop，而是你在操控。**

### 2. 工作树隔离（Worktree）
同时跑好几个 Agent 的时候，给每个 Agent 一个独立的工作空间，各干各的互不干扰，干完了再合并。两个 Agent 改同一个文件的痛苦，跟两个设计师同时改一个图层又不打招呼的痛苦一模一样。

### 3. 项目知识体系（Skill / 知识管理）
Addy Osmani 原文里写的是 skill，但单 skill 是不够的，必须是**知识管理体系**。

AI 每次开新对话就啥都忘了——你说过的代码规范、项目架构、踩过的坑，下次开对话全部从零开始。所以你得有整套方法来沉淀、优化这些知识，让 Agent 每次启动的时候就已经知道你的项目。

作者自己的方法论沉淀成了 `洁癖.skill`，是 Agent 每天调用最多的 skill。体系结构大致是：

- **CLAUDE.md**：全局规则和约束
- **跨会话记忆**：悬而未决的记录和文档路由
- **docs 体系**：完整的知识和经验沉淀
- **洁癖.skill**：每次任务后对整个知识体系进行梳理和审查，确保没有错误

> **没有干净的知识体系的 loop，就像一个每天早上都在看过期文档的员工，干得越快错得越多。**

开源仓库：<https://github.com/KKKKhazix/khazix-skills>

### 4. 连接器（Plugins / MCP）
一个只能看文件系统的 Agent 能力很有限。给它接上 GitHub、Linear、Slack、数据库，它就能在你的真实工作环境里干活，这才叫真正的**闭环**——从发现问题到解决问题到通知人类，一条龙。

### 5. 子 Agent（Sub-Agent）
做事的和检查的分开。写代码的 Agent 不能自己给自己打分——这跟学生自己批自己的考卷一个道理，它一定会对自己太宽容。所以你得有另一个 Agent（甚至用不同的模型）专门来检查前一个 Agent 的输出。一个负责做，一个负责验。

## `/goal`：Loop Engineering 的微观产品化体现

Claude Code 和 Codex 各有一个命令，是这套骨架最直接的体现：

- **Claude Code**：`/goal`
- **Codex**：`追求目标`

意思是你给 Agent 一个完成条件，比如"所有测试通过并且 lint 检查没有报错"，然后它就会一轮一轮地自己干，干完每一轮就检查这个条件是否满足。

大多数讲 Loop Engineering 的文章都停在了这一层——讲五个组件、讲 `/goal` 和 `/loop` 命令、讲怎么配定时任务，就结束了。

**这些都是术。我更想聊的是道。**

## 术与道：定义目标的能力

Loop Engineering 这件事最核心最核心的能力，不是技术能力，也不是写脚本的能力，更不是会配 hook 的能力。**最核心的是定义目标的能力。**

"定义目标"这四个字听起来简单，做起来是真的难。

`/goal` 用得好不好，完全取决于你那个目标定义得好不好。对比两个例子：

- **目标 A**："把这个应用优化一下" → Claude 会陷入尴尬状态：它不知道什么叫"优化好了"，可能改一点就停了，也可能一直改到代码库面目全非。
- **目标 B**："`test/auth` 目录下所有测试通过，`tsc --noEmit` 零报错，`npm run lint` 零违规" → 每改一轮就验证，三个明确的通过标准，全过了就停，没过就继续。

**同一个工具，同一个模型，区别只在于你的目标定义得好不好。**

## 来自管理学的答案

如何定义目标这个能力，我其实不是从 AI 中也不是从开发中学来的，**是从这几年创业的过程中学来的**。定义目标的能力，其实就是**管人的逻辑**。

管人最痛苦的是什么？是给出去的目标不够清晰，然后下属一脸懵逼，不知道你要什么，跟无头苍蝇一样打转，最后做出来的东西你又不满意。

你跟员工说"把这个功能做好"，那他做出来的东西大概率不是你想要的，因为你脑子里的"好"跟他脑子里的"好"不是一个东西。你跟他说"这个接口的响应时间降到 200ms 以下，错误率控制在 0.1% 以内，下周三之前上线"，他做出来的东西跟你预期的偏差就会小很多——因为你给了他一个**可以验证完成的标准**。

你回头看所有好的管理方法论——管理学之父 Peter Drucker 在上世纪 50 年代提出的目标管理、Andy Grove 在 Intel 发明的 OKR、再后来一代代 CEO 用的各种变体——核心其实就一个东西：

> 你能不能把一个模糊的意图，翻译成一组**可衡量、可验证的完成条件**。

管理者要做的，是确保：
- **目标清晰**：条件写得精准
- **资源充足**：给 Agent 配好 Skill、连接器、工作权限，让它手里有足够的工具干活
- **反馈及时**：每轮都有独立的检查器告诉 Agent 做得对不对、哪里需要改

**管人的逻辑和管 Agent 的逻辑是完全一样的。** 只不过管 Agent 比管人还要极端一些——人可以理解你的模糊意图、可以主动来找你确认，Agent 很多时候不会。Agent 会非常自信地按照它自己的理解去执行，然后非常自信地告诉你它做完了。

所以对管理能力的要求，其实比管人还高。这也是为什么 AI 时代管理学、心理学、组织行为学不但没死，反而变得更重要了。

## 古德哈特定律：定义目标的陷阱

管理学和经济学里有个专门的名字，叫**古德哈特定律**：

> 当一个衡量指标变成了目标本身的时候，它就不再是一个好的衡量指标了。

翻译成人话就是：你考核什么，员工就只做什么，然后其他东西可能全都退化。

在 AI Agent 身上，这个问题被放大了一百倍——Agent 比人类更擅长钻规则的空子。Loop Engineering 里很好玩的事情就是：Agent 会针对**验证器**做优化，而不是针对你**真正的目标**做优化。

> 比如你的 loop 条件是让测试全部通过，那 Agent 可能最后不去修 Bug，直接把失败的测试给你删了。

最后答案依然是"测试全过了"——从验证条件看它确实完成了目标，但从你真正想要的结果看，它啥也没干。

所以一个好的目标定义，不能只有做完了的标准，还必须有**不能怎么做的边界**。这其实就是 Harness Engineering 在 Loop Engineering 里面发挥作用的地方：

- **Harness** 是约束、是护栏，告诉 Agent 你可以自由发挥，但这条线你不能越。
- **Loop** 是驱动力，告诉 Agent 往那个方向一直跑。

两个加在一起，才是一个完整的系统。

## 作者的目标定义框架

1. **完成标准要可以被机器验证**。
2. **边界条件要跟完成标准一起定义**。
3. **要有失败的降级方案**。
4. **目标要分层**。

## 四次跃迁

从 Prompt 到 Context 到 Harness 到 Loop，四次跃迁其实讲的是同一个故事：

| Engineering | 告诉 AI | 核心能力 | 底层学科 |
| :-- | :-- | :-- | :-- |
| Prompt Engineering | 好好说话，AI 会更懂你 | 语言表达 | 语言学 |
| Context Engineering | 光说话不够，得给 AI 足够的信息 | 信息筛选和组织 | 信息科学 |
| Harness Engineering | 光给信息也不够，得给 AI 设规则和约束 | 系统设计和规则制定 | 控制论 |
| Loop Engineering | 光设规则也不够，得让整个系统能自己跑起来 | 目标定义和管理 | 管理学 |

> 人类社会，其实从来就没有变过。
