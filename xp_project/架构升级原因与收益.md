# 车机语音助手架构升级：从 NLU-Workflow 到 ReAct + ToolCall

> 面试表达主线（二轮/三轮技术面）：
>
> 我主导/参与了车机语音助手的核心架构升级，把传统的 `ASR → NLU → Workflow → 子领域技能` 的**规则驱动**架构，重构为 `ASR → ReAct Agent → Tool Calling` 的**模型驱动**架构。这不是一次简单的"接大模型"，而是一次从**功能型语音系统**到**具备规划能力的智能体系统**的架构跃迁。下面我从"为什么做、怎么做、收益是什么、踩了哪些坑"四个维度讲清楚。

---

## 一、为什么要改造：旧架构已经触顶

面试时先讲清楚**问题是真实存在的**，而不是为了用大模型而用大模型。

### 1.1 技能烟囱化，研发成本随域数线性增长

传统车机按领域拆分：导航域、音乐域、空调域、车控域、电话域、百科域……

每个域都是一套独立的：

- 独立 NLU 模型 / 语料
- 独立 Workflow / 状态机
- 独立上下文与槽位管理
- 独立兜底与澄清策略

结果就是：

```text
新增一个技能 ≈ 新建一个子系统
```

**量化感受**：团队后期大约 70% 的人力花在**维护存量规则和修回归**，只有不到 20% 在做真正的新能力。

### 1.2 NLU 天花板明显，长尾表达覆盖不动

传统 NLU = `意图分类 + 槽位填充 + 规则/语法`。

但用户真实表达是高度口语化、长尾的，比如都要映射到"空调控制"：

- "我有点冷"
- "帮我凉快一点"
- "太阳太晒了"
- "后排说热"

传统解法只能靠**同义词扩展 + 语料标注 + 规则堆积**，边际成本越来越高，而且永远覆盖不全。

### 1.3 多轮与跨域能力弱，复合指令几乎无解

真实高频场景：

> "帮我找个安静的咖啡馆，然后导航过去，顺便把座椅加热打开。"

传统架构下这类 query 的问题：

- **多意图冲突**：NLU 只能出一个主意图
- **跨域状态难同步**：POI 检索的结果要传给导航域，还要触发车控域
- **Workflow 编排爆炸**：条件树/状态机膨胀到无法维护

最终结果：复杂 query 要么降级成单步，要么失败。

### 1.4 Workflow 脆化，回归成本吞掉迭代速度

```text
if intent == A: goto X
elif intent == B: goto Y
elif intent == C and slot.xxx: goto Z
...
```

随着技能数量增长，条件树和状态机呈指数级膨胀，**改一个意图，牵连一片回归**。到了后期，系统的"可演进性"基本被锁死。

## 二、新架构：ASR + ReAct Agent + ToolCall

### 2.1 架构总览

```text
ASR
  ↓
Memory / Context（对话历史 + 车况 + 用户画像）
  ↓
ReAct Agent（Planner + Reasoner）
  ↓
Tool Calling（结构化调用协议）
  ↓
工具执行层（导航 / 车控 / 媒体 / 天气 / 搜索 / 知识库 / 系统 API / MCP）
  ↓
结果整合 & TTS
```

### 2.2 核心变化

| 维度 | 旧架构 | 新架构 |
|---|---|---|
| 驱动方式 | 意图分类 + 槽位填充 | 语言理解 + 推理规划 |
| 编排方式 | 静态 Workflow | 模型动态规划 |
| 能力组织 | 子域烟囱 | 工具（Tool）平台化 |
| 多轮/跨域 | 手写状态机 | 模型原生支持 |
| 扩展成本 | 新域 = 新子系统 | 新能力 = 新 Tool |
| 模型红利 | 与 NLU 深耦合，升级收益有限 | 模型越强，系统越强 |

### 2.3 模型在新架构里承担的职责

- 意图理解（含长尾、口语化）
- 任务拆解与多步规划
- 工具选择与参数补全
- 多轮追问与澄清
- 执行结果的整合与回复生成

### 3.1 可扩展性：从"加子系统"到"加一个 Tool"

这是**最大**的收益，也最容易让面试官 get 到。

- 旧：新增"查充电桩" = 新 intent + 新 slot + 新 domain + 新 workflow + 新语料
- 新：新增"查充电桩" = 注册一个 Tool Schema：

```json
{
  "tool": "search_charge_station",
  "description": "查询附近可用充电桩",
  "args": {
    "city": "string, optional",
    "battery_level": "number, optional"
  }
}
```

**量化收益**（⚠️ 参考值，需校正）：

- 新能力上线周期：从 **10-15 人日 → 1-2 人日**，**提速约 8-10 倍**
- 迁移期内累计 Tool 化能力数：**80-150 个**（覆盖导航 / 车控 / 媒体 / 天气 / 百科 / MCP 外部工具等）
- 新技能回归用例数：从 **200-400 条 → 30-80 条**（只测自身 Tool + 规划层黄金集）

### 3.2 产品能力：跨域协同从"不可能"到"默认能力"

Agent 天然支持**任务拆解 + 工具串联**，这是旧架构靠手写 workflow 根本做不到的。

例子："找个安静的咖啡馆，导航过去，打开座椅加热"：

```text
Thought: 需要先检索 POI → 拿到地址后调导航 → 并行触发车控
Action 1: search_poi(keyword="安静咖啡馆")
Action 2: start_navigation(dest=...)
Action 3: set_seat_heater(on=true)
```

**量化收益**（⚠️ 参考值，需校正）：

- 复合/跨域指令成功率：**30-50% → 80-90%**
- 可支持的复合指令模板数：从硬编码的 **20-50 条** → 模型泛化覆盖 **数百到数千种组合**
- 端到端任务完成率（多步任务）：**55-65% → 85-92%**

### 3.3 用户体验：从"命令式"到"自然对话"

旧架构：用户必须学会系统的"话术"。
新架构：系统去理解用户的自然表达。

典型例子："我困了" —— 模型可以推理出组合动作：

```text
→ 开窗通风
→ 空调调低 2 度
→ 播放提神音乐
→ 提示"前方 5km 有服务区，要不要停一下？"
```

**量化收益**（⚠️ 参考值，需校正）：

- 长尾 query 覆盖率：**60-70% → 88-93%**
- 首轮命中率：**70-80% → 88-94%**
- 平均澄清轮次：**1.6-2.2 → 1.05-1.2**
- 用户 NPS / 满意度：**+10-15 分**
- 语音功能**日活渗透率**（DAU/车辆活跃数）：**+15-25%**
- 周活用户平均交互次数：**+30-50%**

面试时要强调：**不要只看单轮时延，要看"任务完成时间"和"完成率"**，这是车机语音真正的北极星指标。

### 3.4 时延：分场景看，整体可接受甚至更优

面试官一定会追问"加了 LLM 时延不是更高吗？" —— 这是必答题。

**拆开讲**（⚠️ 参考值，需校正；时延指 ASR 完成 → 第一个可感知响应的 P95）：

| 场景 | 旧架构 P95 | 新架构 P95 | 说明 |
|---|---|---|---|
| 简单单域指令（"打开空调"） | 500-800 ms | 800-1200 ms | 多了一次 LLM 调用，端侧 7B 可控 |
| 复杂复合指令 | 2500-4000 ms | 1500-2500 ms | **反而更低**，省掉多次 orchestration |
| 多轮澄清场景（完成任务总耗时） | 8-15 s（3-5 轮） | 3-5 s（1-2 轮） | **任务完成时间降 60%+** |

**关键分解指标**（端侧 7B / INT4 量化）：

- LLM 首 token 延迟：**250-400 ms**
- LLM 平均生成长度：**20-60 tokens**，生成时延 **150-400 ms**
- Tool 调用执行（导航 / 车控 本地 RPC）：**50-200 ms**

**优化手段**（面试加分项）：

- 端侧小模型（7B/13B）+ 云端大模型分层：简单意图端上走，复杂规划云上走；典型**端云命中比 7:3**
- **流式 Tool Call**：ASR 完成即触发 POI 预取等前置 Tool，并行节省 **200-400 ms**
- **工具结果缓存 + 会话级 Memory**：重复调用命中率 **15-25%**
- **Prompt 精简 + KV Cache 复用**：首 token 延迟降 **30-50%**
- **推测解码 / 小模型草稿 + 大模型验证**：生成时延再降 **20-30%**

### 3.5 成本：短期推理成本↑，长期总成本↓

面试要讲**总拥有成本（TCO）**，不要只看推理账单。

**上升的成本**（⚠️ 参考值，需校正）：

- LLM 推理：单次请求 **0.002-0.01 元**（云端 GPT-4 级 0.005-0.02 元，自研 7B/13B 可降到 0.001-0.005 元）
- 按单车日均 **30-50 次**交互估算，月推理成本约 **2-15 元/车**
- 端侧 NPU 算力占用提升 **20-40%**（需更新 SoC 选型或量化方案）

**下降的成本**（大头）：

1. **规则工程人力**：NLU 标注 + 规则维护团队规模可压缩 **50-70%**
2. **多域重复建设**：Tool 一次封装、多 Agent（车机 / 手机 App / 运营后台）复用，复用率 **60%+**
3. **联调成本**：跨团队对齐从私有协议统一到 `tool_name / schema / result`，联调周期 **3-5 天 → 0.5-1 天**
4. **回归测试成本**：逻辑从代码搬到 Prompt + Schema，回归用例缩减 **60-75%**

**净 TCO 变化**（⚠️ 参考值）：

- 纯推理账单：**+30 ~ +80%**
- 研发/维护人力：**-40 ~ -60%**
- **端到端 TCO：净下降 20-35%**
- **投资回收期**：大规模上量后 **6-12 个月**

### 3.6 战略收益：架构具备"模型红利"

旧架构和 NLU 深耦合，模型升级带来的收益有限。
新架构下，**基座模型每升级一代，系统能力自动变强**：

- 推理更准 → 工具选择更准
- 多轮更稳 → 任务完成率更高
- 指令遵循更好 → 参数补全更准

**量化感受**（⚠️ 参考值）：基座模型每次大版本升级（如 7B → 13B，或换更强底座），**无需改任何业务代码**，整体任务成功率可再提升 **3-8pp**，长尾覆盖率再提升 **5-10pp**。

这对领导/面试官来说是一句关键话：

> **我们把架构做成了"模型红利的承接器"，而不是一次性替换。**

## 四、关键技术挑战与取舍（面试深挖区）

二轮/三轮面试官一定会往深了问，准备好这几个点。

### 4.1 如何保证 Tool Call 的稳定性？

- **Schema 强约束**：JSON Schema + 参数校验，模型输出非法直接拒绝并重规划
- **Function Calling 原生能力**：优先用模型原生的 function call 而不是纯 Prompt 拼
- **Tool 幂等性 / 补偿**：车控类动作设计幂等，失败可安全重试
- **安全域隔离**：车控类高危 Tool 走白名单 + 二次确认

### 4.2 如何做端云协同？

- 端侧小模型负责：ASR、简单意图、隐私相关 Tool、兜底
- 云端大模型负责：复杂规划、长尾理解、知识密集型任务
- **路由策略**：基于意图置信度 + query 复杂度 + 网络状况动态切换

### 4.3 如何控制幻觉和错误工具调用？

- Tool Schema 里明确 `description` + `when_to_use` + `examples`
- 关键动作加**执行前确认**（如"确认要导航到 XX 吗？"）
- 引入**评估集 + 回归**：每次 Prompt / 模型变更跑一遍黄金集

### 4.4 如何从旧架构平滑迁移？

- **双轨运行**：旧 NLU 作为 fallback，Agent 置信度低时降级
- **Tool 化优先**：先把存量子域封装成 Tool，再逐步把流量切到 Agent
- **灰度 + 分场景切换**：简单域先切，复杂域后切

### 4.5 可观测性怎么做？

- 每次交互记录：`user_query → thought → tool_calls → tool_results → final_response`
- 关键指标：任务成功率、工具调用准确率、规划步数、端到端延迟、澄清轮次
- **Bad case 回流**：直接沉淀为评估集或 Prompt few-shot

---

## 五、一句话总结

> 这次架构升级，本质是从**"规则驱动的功能系统"**跃迁到**"模型驱动的智能体系统"**：
>
> **ToolCall 让能力平台化，ReAct 让系统具备自主规划，大模型负责统一的理解与决策** —— 这让我们在可扩展性、产品能力和用户体验上都拿到了量级提升，同时通过端云协同和分层优化，把时延和成本控制在了可接受范围，更重要的是，这套架构能**持续吃到基座模型演进的红利**，是未来智能座舱的核心基础设施。

## 附：常见追问 Cheat Sheet

| 追问 | 回答要点 |
|---|---|
| 为什么不直接用大模型端到端输出控制指令？ | 不可控、不可审计、车控安全不允许；Tool Call 是**可控的动作边界** |
| ReAct 和 Plan-and-Execute 怎么选？ | 简单任务 ReAct，复杂长链路任务上 Plan-and-Execute；我们做了混合策略 |
| 端侧模型选型？ | 7B/13B 量级，Int4/Int8 量化，NPU 部署；重点看指令遵循和 Function Call 能力 |
| 怎么评估 Agent 效果？ | 任务成功率 + 工具调用准确率 + 规划步数 + 用户满意度（NPS）+ 人工评测黄金集 |
| 车机离线场景怎么办？ | 端侧模型 + 本地 Tool 白名单，保证高频指令离线可用 |
| Prompt 怎么管理？ | 版本化 + A/B + 回归评估集，Prompt 当代码管 |
