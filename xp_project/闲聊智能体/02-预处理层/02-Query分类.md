# Query 分类

> 预处理层核心模块｜意图路由与能力调度枢纽

---

## 1. 能力定位

Query 分类的目标不是打一个语义标签，而是决定**后续链路如何调度**：

- 走哪条**推理链路**（闲聊推理层 vs. 搜索增强层）
- 用哪个**模型**（对话模型 / 推理模型 / 轻量模型）
- 调用哪些**工具/插件**（搜索引擎 / 实时 API / 计算器 / 日历）
- 注入哪套**Prompt 片段**（情感陪伴 / 叙事引导 / 思维链…）

分类结果是一张「调度指令单」，下游各模块按指令单执行，而不是各自再判断意图。

---

## 2. 分类体系（12 个标签，一级平铺）

所有标签同级，分类器输出置信度最高的单一标签；置信度不足时兜底走 `casual_chat`，无需强行归类。

### 2.1 联网查询群（3 类）

需要借助外部信息源回答，模型自身知识不可靠。按**用户意图**细分：

| 标签 | 用户意图 | 代表 Query | 数据源 |
|------|---------|------------|--------|
| `web_news` | 查资讯——想知道发生了什么 | "最近有什么热点"、"今天头条新闻" | 搜索引擎 + 新闻聚合 |
| `web_data` | 查数据——想要一个精确的实时数值 | "茅台今天股价"、"今天天气"、"欧元汇率" | 实时专用 API（行情/天气/汇率…） |
| `web_knowledge` | 查知识——想了解模型盲区的专业内容 | "最新的 Transformer 变体论文"、"某专利的具体内容" | 学术库 + 搜索引擎 |

> **三者共同判断标准**：模型自身无法可靠回答（知识截止 / 实时性 / 第三方来源）

### 2.2 陪伴问答群（2 类）

高频核心，是本智能体的主战场。不需要联网，但需要专属 Prompt 模式。

| 标签 | 场景定位 | 代表 Query | 核心诉求 |
|------|---------|------------|---------|
| `emotion_chat` | 情感陪伴——用户有情绪，需要被看见和回应 | "今天好累"、"我失恋了"、"最近压力好大" | 共情优先，回应情绪，不急于给建议 |
| `qa_knowledge` | 知识问答——有确定性问题，想要准确答案 | "黑洞是怎么形成的"、"二战是哪年结束的"、"光合作用的原理" | 准确第一，常识科普方向，不接 RAG，依赖模型内置知识 |

> **两者的边界**：是否有「明确要查的事实」。情绪类 Query 即使包含知识点，也优先走情感陪伴。

> **`qa_knowledge` 的知识范围**：定位**常识科普**（历史、科学、地理、文化等），模型内置知识可覆盖，不接 RAG。若用户问到时效性强或专业度极高的内容，置信度会偏低，自然向 `web_knowledge` 漂移。

### 2.3 娱乐创作群（3 类）

用户想要一个「有形态」的内容输出，Prompt 策略差异显著。

| 标签 | 代表 Query | 模型输出形态 | Prompt 核心策略 |
|------|------------|------------|----------------|
| `joke` | "讲个笑话"、"说个谐音梗"、"来个冷笑话" | 一段幽默文字 | 多样性拉满，语言轻快，避免解释为什么好笑 |
| `story` | "讲个睡前故事"、"编个关于 AI 的故事" | 有完整结构的叙事 | 起承转合引导，情节要有张力，结尾不能烂尾 |
| `poetry` | "帮我写首诗"、"写个藏头诗"、"来首七言绝句" | 格律化文字 | 格律 / 意境优先，输出格式化，字数严格 |

### 2.4 计算工具群（2 类）

需要精确计算，纯语言模型推理**不可靠**，必须走工具调用。

| 标签 | 代表 Query | 工具依赖 | 为什么不能用模型直接算 |
|------|------------|---------|---------------------|
| `math` | "23 的 17 次方是多少"、"帮我算这道微积分" | 计算器插件 / 代码解释器 | 大模型多步数值计算误差率高，复杂题会编造过程 |
| `date_calc` | "距元旦还有几天"、"上周三是几号"、"明天星期几" | 日历 / 系统时间 API | 大模型不知道"今天"是哪天，直接算必错 |

### 2.5 兜底群（2 类）

| 标签 | 触发条件 | 处理方式 |
|------|---------|---------|
| `casual_chat` | 日常寒暄、意图不明确、置信度不足无法归类 | 走通用闲聊 Prompt，高多样性，宽容回复 |
| `reject` | 政治敏感、色情暴力、人身攻击等 | 前置拦截，不进推理层，返回固定拒答话术 |

> `casual_chat` 同时承担两个角色：**日常聊天 + 所有垂域的兜底**。分类置信度不足时，宁可走这里，也不强行归垂域。

## 3. 下游调度指令矩阵

分类结果触发的三层调度：

| 标签 | 推理链路 | 模型选型 | 工具/插件 | Prompt 片段 |
|------|---------|---------|----------|------------|
| `web_news` | 搜索增强层 | 中等对话模型 | 搜索引擎 API | 资讯摘要 + 口语化改写 |
| `web_data` | 搜索增强层 | 中等对话模型 | 实时专用 API | 数据读取 + 人设融合 |
| `web_knowledge` | 搜索增强层 | 大模型 | 学术库 + 搜索引擎 | 知识综合 + 引用溯出 |
| `emotion_chat` | 闲聊推理层 | 情感对话模型 | — | 情感陪伴片段（共情 + 追问） |
| `qa_knowledge` | 闲聊推理层 | 大模型 | — | 知识问答片段（准确 + 简洁，常识科普方向） |
| `math` | 闲聊推理层 | 推理模型（o系） | 计算器 / 代码解释器 | 思维链片段（步骤拆解） |
| `date_calc` | 闲聊推理层 | 轻量模型 | 日历 / 系统时间 API | 简洁回复片段 |
| `joke` | 闲聊推理层 | 对话模型 | — | 幽默片段（多样性最高） |
| `story` | 闲聊推理层 | 大模型 | — | 叙事片段（起承转合结构） |
| `poetry` | 闲聊推理层 | 大模型 | — | 格律片段（字数 + 意境约束） |
| `casual_chat` | 闲聊推理层 | 对话模型 | — | 通用闲聊 Prompt |
| `reject` | 拦截 | — | — | 固定拒答话术库 |

## 4. 分类器设计

```yaml
classifier:
  model: "intent-classifier-v3"
  # 轻量定制分类模型，P50 延迟 < 20ms
  # 只做分类，不做生成，不需要大模型

  output:
    label:       # 12 个一级标签，单标签输出
      - web_news | web_data | web_knowledge
      - emotion_chat | qa_knowledge
      - joke | story | poetry
      - math | date_calc
      - casual_chat | reject
    confidence:  0.0 ~ 1.0   # 最高置信标签的得分

  routing_rule:
    - if label == reject           → 拦截，不进推理层
    - if label in [web_*]          → 搜索增强层
    - if confidence < 0.65         → 兜底走 casual_chat（不强行归垂域）
    - if label in [math,date_calc] → 闲聊推理层 + 工具调用
    - else                         → 闲聊推理层 + 对应 Prompt 片段注入
```

**边界冲突处理**：
- 单标签输出，取置信度最高者，不做多标签融合
- 置信度 < 0.65 时，无论最高标签是什么，一律走 `casual_chat` 兜底
- 用户故意混合垂域（如"讲个数学笑话"）→ 置信度哪个高走哪个，`casual_chat` 有概率兜底，接受这个结果

## 5. 关键决策

**为什么按用户意图而非数据源来细分联网查询？**

按数据源分（API / 搜索 / 学术库）是后端实现视角，用户不关心；按意图分（查什么）才能决定**回复的语气和形态**：
- 查资讯 → 快速摘要 + 话题延伸
- 查数据 → 精确数值 + 口语化解释
- 查知识 → 结构化解读 + 引用溯出

**为什么情感陪伴和知识问答单独立出来，而不并入 casual_chat？**

两者下游的 Prompt 策略和成功标准完全不同：
- 情感陪伴的评测指标是「用户是否感到被理解」，共情 > 准确
- 知识问答的评测指标是「答案是否正确」，准确 > 流畅

合并进 `casual_chat` 会导致二者都做不好。

**两种多轮对话的不同策略**：

本智能体内存在两种典型多轮模式，上下文管理策略不同：

| 多轮类型 | 典型标签 | 上下文重点 | Session 策略 |
|---------|--------|------------|----------|
| **知识深入追问** | `qa_knowledge` | 上一轮的问题主题、已展开的子问题 | 局部摔要就够，保留话题线索，不需要全量历史 |
| **情感陪伴持续对话** | `emotion_chat` | 用户的情绪状态、已说过的事情细节 | 全量轮次保留更高上限，操心要记住用户说的每一件事 |

> 双种多轮均需要到 Session 管理模块支撑，详见「06-基础能力/01-多轮上下文管理.md」。

**为什么 `qa_knowledge` 不接 RAG？**

定位是常识科普，模型训练语料已包含大量常识，接 RAG 不带来额外收益，却增加延迟和成本。若用户问的是时效性强或极专业的内容，分类器置信度会下降，自然向 `web_knowledge` 漂移。

**为什么 math/date_calc 不合并为一个计算类？**

路由差异太大：`math` 走推理模型 + 计算器插件，`date_calc` 走轻量模型 + 日历 API，两条完全不同的工具链，合并后路由层需要再判断，不如在分类时就区分。

## 6. 答辩问答预设

> Q：12 个标签，分类器怎么保证准确率？
> A：分类器是领域定制的轻量模型，12 类远比开放域 NLU 简单。核心是训练数据质量：每类准备 500~1000 条真实用户 Query，覆盖主流表达和边缘变体。关键指标是**各类 Precision**：reject 的 precision 必须 > 99%（漏拦比误拦更危险），math / date_calc 的 recall 必须 > 95%（分错会编造答案）。

> Q：情感陪伴和普通闲聊的边界怎么划？
> A：核心判断是「用户是否在表达情绪状态」。有情绪词（累/难过/烦/失落）、有情境描述（我今天…/最近…）的，走 `emotion_chat`；纯粹话题性聊天（聊天气、聊电影）走 `casual_chat`。灰色地带接受分错，因为两条链路的 Prompt 差异主要是共情引导的有无，分错后用户体验降级有限。

> Q：为什么不用大模型直接做分类，还要单独训练一个分类器？
> A：大模型做分类延迟高（500ms+）、成本高，而且路由逻辑混入了主模型，无法独立迭代和 AB 实验。轻量分类器 < 20ms，可以独立更新，分类错误时有置信度兜底，整体风险可控。

> Q：联网查询为什么按用户意图切，而不按数据源切？
> A：按数据源切（API/搜索/学术库）是**后端实现视角**，用户不关心数据从哪来；按意图切（查资讯/查数据/查知识）才能决定**回复的语气和形态**：查资讯要快速摘要+话题延伸，查数据要精确数值+口语化解释，查知识要结构化解读+引用溯出。数据源的选择是搜索增强层的内部实现细节，分类层不需要了解。

> Q：数学题不用大模型推理，要用工具，工具出错了怎么办？
> A：工具出错比模型编造答案好很多——工具返回的错误是确定性的（比如网络超时、API 异常），模型可以带小错误外显式告知用户而不是静默编造。工具返回不可靠时的优先道歉并引导用户拆解步骤自行验算，而不是编造一个看起来像答案的数字。

> Q：`casual_chat` 就是各类的兜底，这会不会让垃圾数据流进模型，影响质量？
> A：`casual_chat` 的尃底不是降低质量，而是寻找安全落地点。普通闲聊用户对“聊天天气却没得到天气数据”容忍度远高于对“更一下天气却得到一个错误数字”。兜底到闲聊，用户最多返回一句不相关的回复，而不是接到错误数据就信了。

> Q：用户的 Query 是混合的，比如“我心情不好，天气怎么样”——情感 + 联网查询，怎么处理？
> A：单标签输出，取置信度最高的一个。这个例子里情绪表达带天气查询，模型最高置信标签是 `emotion_chat` 的概率更高，于是走情感陪伴链路，先回应情绪。天气信息可以通过后续轮由用户主动再问获取，也可以在 Prompt 里引导模型在情绪回应后顺带天气一句。

> Q：分类器训练数据怕没有，冒冷阶段怎么办？
> A：冷启动有两个方案。一是用通用分类模型先顶着，表现不会太差但没有领域优化；二是用 GPT-4 对种子 Query 批量打标签生成初始训练集，优先保证 reject 、math 、date_calc 三个高风险类的精确率，其他类先低标准上线，边收用户真实标注边迭代。

> Q：标签多了不就意味着每个类的样本量要减少，分类器会不会因此变差？
> A：初始训练集是按类和采样的，不是均分。高风险类（reject/math/date_calc）就稍微多备些训练样本；自然流量大的类（casual_chat/emotion_chat）特意控制样本量防止压制小类。同时训练时进行类间平衡采样，类内多要覆盖表达式多样性而非简单堆数量。

> Q：分类上线后效果怎么评估？用什么指标衡量分类器的价值？
> A：分类器本身看 offline 测评集的准确率，但它的真正价值要用下游指标衡量：数学题命中 math 后模型答错率是否下降、情感话题命中 emotion_chat 后用户满意度是否提升、联网查询命中 web_* 后回复准确率是否提升。分类器是中间环节，用端到端指标降水来驱动分类器迭代。
