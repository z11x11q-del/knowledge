# 闲聊智能体全链路设计

> 技术设计文档｜闲聊智能体从 Query 入口到回复下发的全链路能力拆解
> 能力边界：**闲聊对话** + **联网查询**，不含导航、媒体播放、车控等执行型技能
> 核心目标：把闲聊做深、把联网查询做准，让智能体在非任务场景下真正「好用」
> 适用场景：技术答辩（智能对话方向）、团队架构评审、系统设计讨论

---

### 1.2 设计原则

| 原则 | 含义 |
|------|------|
| **可插拔** | 每一层都是独立组件，可按需开关；改写模块可整体绕过 |
| **全链路可观测** | 每个节点打 trace_id，延迟和错误从接入到下发全程可追 |
| **实验优先** | 所有关键决策节点都接 AB 实验框架，用数据驱动迭代 |
| **分级降级** | 模型/网络异常时逐级切换，不依赖单点稳定性 |

## 二、核心能力模块详解

> 通用语音能力（唤醒、ASR、VAD、TTS、打断、拒识）参考 [[car_voice_wiki/03-语音能力]] 子目录

### 2.1 Query 改写

**能力定位**：在用户原始输入进入分类和推理之前，将口语化、残缺、含歧义的表达改写为模型友好、语义完整的标准文本。

**改写子任务**：

| 子任务 | 问题场景 | 改写示例 |
|--------|----------|----------|
| 口语纠错 | "你能帮我讲个笑hua吗" | → "你能帮我讲个笑话吗" |
| 指代消解 | "他说的那首歌是什么" | → "上一轮提到的周杰伦的歌是什么" |
| 省略补全 | "再来一个" | → "再讲一个笑话" |
| 复杂句拆分 | "帮我查天气然后推荐穿什么" | → 拆成两个子意图分别处理 |
| 语义规范化 | "我心情超级不好嗷嗷" | → "我现在心情很差" |

**架构设计**：

```
原始 Query
    ↓
[规则改写] 口语纠错、标点规范（轻量、低延迟）
    ↓
[模型改写] 上下文相关的指代消解、省略补全（可配置是否开启）
    ↓
改写后 Query → 写入 trace，同时保留原始 Query 备用
```

**关键决策**：
- 改写模块**可按 Query 类型动态跳过**：简单问候类（"你好"、"在吗"）无需改写，直接透传
- 模型改写引入**改写置信度**，低于阈值时回退到原始 Query，避免过改写劣化语义
- 改写结果写 trace，评测层可对比改写前后的最终回复质量，形成闭环

**答辩问答预设**：
> Q：为什么不直接把口语化 Query 扔给 LLM，让它自己理解？
> A：两个原因。第一，改写可以解决**上下文依赖**（多轮对话中的指代消解），LLM 接收的 Prompt 上下文窗口有限，改写后的单轮 Query 更干净；第二，改写后的 Query 可以**被复用**——分类模块、缓存模块、评测模块都能拿标准化后的 Query 做更精准的处理。

### 2.2 Query 分类

**能力定位**：对改写后的 Query 做意图路由，核心目标是判断当前请求**需要什么能力加持**：是否需要联网补充实时/盲区知识，是否需要特定垂域技能，还是纯靠模型对话能力即可。分类结果决定后续链路的调度方式，是整个智能体的"交通枢纽"。

**五类路由体系**：

| 类别 | 判断标准 | 代表 Query | 处理路径 |
|------|----------|------------|----------|
| **纯闲聊** | 情感表达、话题聊天、日常闲聊 | "今天心情不好"、"聊聊吧"、"你喜欢什么食物" | 闲聊推理层 |
| **联网查询** | 需要实时数据，或模型训练语料盲区 | "今天股票头条"、"最新 AI 论文"、"这两天有什么新闻" | 搜索增强层 |
| **垂域能力** | 需要特定技能加持，不需联网 | "计算一道数学题"、"讲个笑话"、"给我讲个故事" | 闲聊推理层（垂域 Prompt） |
| **拒答** | 政治敏感、色情暴力、评个人得失 | 各种违规请求 | 前置拦截，返回拒答话术 |
| **兜底** | 意图模糊、置信度过低 | 语义不明的 Query | 澄清追问或默认纯闲聊 |

> 注：导航、媒体播放、车控等执行型指令不在本智能体处理范围内，由上游路由在此之前已分流至对应技能模块。

**联网查询类的两种子场景**：

联网查询类内部进一步分两种子意图，它们的共同点是「**模型自身不能可靠回答**」：

| 子场景 | 判断标志 | 代表 Query | 检索策略 |
|----------|----------|------------|----------|
| **实时信息** | 模型知识有截止日，且答案随时间变化 | 股价、新闻热搜、天气、汇率、赛事比分 | 实时 API 优先 + 搜索引擎备用 |
| **盲区知识** | 训练截止日后发生的事实，或第三方专业文档 | 最新学术论文、特定领域专业知识、小众资料 | 搜索引擎 + 学术库接口 |

**垂域能力类的子意图拆解**：

垂域能力类不需要联网，但需要将对应的垂域 Prompt 片段注入推理层，让模型"切换属性"：

| 垂域 | sub_intent | 代表 Query | 核心 Prompt 策略 |
|-------|-----------|------------|----------------|
| 数学计算 | `math` | "计算 23 的 17 次方"、"微积分题" | 第一性准确，开启思维链，禁止编造 |
| 日期计算 | `date_calc` | "距元旦还有多少天"、"明天是星期几" | 优先调用日历工具 API，不依赖模型推理 |
| 讲笑话 | `joke` | "讲个笑话"、"说个谐音梗" | 开启幽默流畅模式，多样性拉满 |
| 脱口秀 | `standup` | "让我开心一下"、"跑个段子" | 运动式语言，推理节奏轻快幽默 |
| 讲故事 | `story` | "讲个小故事"、"编一个关于 AI 的故事" | 起承转合结构引导，Prompt 强调情节连贯性 |
| 诗歌创作 | `poetry` | "帮我写首诗"、"写个藏头诗" | 格律 / 意境优先，输出格式化 |
| 其他垂域 | `vertical_other` | 其他有明确输出形态的创作 | 按实际垂域加载对应片段 |

**分类器设计**：

```yaml
classifier:
  model: "intent-classifier-v2"   # 轻量分类模型，P50延迟 < 20ms
  output:
    label: "chat | web_query | vertical | reject | fallback"
    confidence: 0.0 ~ 1.0
    sub_intent: "emotion | math | date_calc | joke | standup | story |
                 poetry | web_realtime | web_blind_spot | vertical_other | ..."
  routing_rule:
    - if confidence < 0.6       → fallback
    - if label == reject        → 直接拒答，不进推理层
    - if label == web_query     → route to search_augment_layer
    - if label == vertical      → route to chat_inference + inject vertical_prompt
    - if label == chat          → route to chat_inference
```

**关键决策**：
- 垂域能力类**不走联网链路**，但进入闲聊推理层时注入对应垂域 Prompt 片段，让模型"切换属性"
- 日期计算类使用日历工具 API，而不依赖模型直接推理日期（大模型日期计算易出错）
- 分类器选**轻量专用模型**而非主模型，分类不需要生成能力，小模型延迟低 10 倍以上
- `sub_intent` 字段附带传递到推理层，帮助 Prompt 选择更精准的垂域模板、调节回复风格

**各类边界判断速查表**：

| 判断维度 | 纯闲聊 | 垂域能力 | 联网查询 |
|----------|--------|----------|----------|
| 是否需要实时数据 | 否 | 否 | 是 |
| 模型训练语料是否覆盖 | 是 | 是 | 否（盲区）或已过时 |
| 是否需要特定能力加持 | 否 | 是（计算/创作/输出格式） | 否 |
| 口语化要求 | 高 | 中（算法须准确） | 中（不宜平铺式展示） |
| 失败代价 | 低 | 中（计算错会投诉） | 高（行情天气错会投诉） |

**灰色地带处理策略**：

```
纯闲聊 vs 垂域能力 的边界：
  识别关键词：如果 Query 包含 "计算/说/讲/写/帮我" 等动词 + 垂域名词，强制归垂域能力类
  否则走 chat + 高多样性 Prompt（宽容普通知识话题）

垂域能力 vs 联网查询 的边界：
  辨别时效性：内容是否随时间变化而变
  辨别盲区：询问的是训练截止日后发生的事实 / 第三方文档

联网查询的子类（实时 vs 盲区）：
  识别时间敏感词（今天/最新/现在/刚刚）→ 实时信息
  识别专业来源词（论文/研究/数据库/文档）→ 盲区知识
```

**答辩问答预设**：
> Q：这么分类太细了，不怕分错吗？为什么不就用大模型直接理解意图？
> A：分类模型是轻量定制模型，延迟 < 20ms，分错的代价是走错链路（比如把数学题走纯闲聊 Prompt，模型会编造答案）而不只是多消耗几个 Token。用大模型直接理解意图不是不可以，但延迟高、成本高，而且路由逻辑耦合到了主模型里、难以独立迭代。分类错误时有兜底默认走纯闲聊路径保底。

------|----------|-----------|
| **闲聊型** | 情感倾诉、话题聊天、开玩笑、脑洞讨论 | 进入闲聊推理链路 |
| **联网查询型** | 天气、百科知识、新闻热点、实时行情 | 进入搜索增强链路 |
| **拒答型** | 政治敏感、色情、人身攻击 | 前置拦截，返回固定拒答话术 |
| **兜底型** | 置信度过低、语义不明 | 触发澄清追问或默认闲聊 |

> 注：导航、媒体播放、车控等执行型指令**不在本智能体处理范围内**，由上游路由在此之前已分流至对应技能模块。

**分类器设计**：

```yaml
classifier:
  model: "intent-classifier-v2"   # 轻量分类模型，P50延迟 < 20ms
  output:
    label: "chat | web_query | reject | fallback"
    confidence: 0.0 ~ 1.0
    sub_intent: "emotion | humor | greeting | ..."
  routing_rule:
    - if confidence < 0.6      → fallback
    - if label == reject       → 直接拒答，不进推理层
    - if label == web_query    → route to search_augment_layer
    - if label == chat         → route to chat_inference
```

**关键决策**：
- 分类器选**轻量专用模型**而非主模型，原因是分类不需要生成能力，小模型延迟低 10 倍以上
- 引入**置信度兜底**避免硬路由错误：置信度低时走保守的默认闲聊，而非强行路由到错误链路
- 子意图字段（`sub_intent`）传递给推理层，帮助 Prompt 选择更精准的人设模板

**关键决策——闲聊 vs 联网查询的边界判断**：

| 判断维度 | 闲聊型 | 联网查询型 |
|----------|---------|-----------|
| 时效性要求 | 低（通用知识、情感表达） | 高（今天天气、最新新闻） |
| 答案唯一性 | 低（见仁见智） | 高（有明确正确答案） |
| 失败代价 | 低（回答差一点用户容忍） | 高（答错天气 / 行情用户会投诉） |
| 是否需要实时数据 | 否 | 是 |

**答辩问答预设**：
> Q：闲聊和联网查询的边界怎么定？有没有灰色地带？
> A：有。比如“给我推荐部电影”，纯模型知识足够，走闲聊；但“今天院线有什么新片”，就必须联网。判断核心是**时效性**：依赖实时数据的走搜索增强，依赖常识/情感的走闲聊。灰色地带我们用**置信度 + 时效性双判断**：模型输出里包含时间敏感词（今天/最新/现在）且置信度 < 0.7，自动触发搜索增强兜底。

### 2.3 联网查询能力

**能力定位**：针对需要实时数据的 Query，走搜索增强生成（RAG-like）路径，而不是纯粹依赖模型迟滞知识回答，是闲聊智能体能力边界向外拓展的核心能力。

**联网查询全链路**：

```
Query 分类为 web_query
    ↓
[查询词提取 & 改写]
  ├─ 从原始 Query 中提取核心搜索词（去除口语完整组成成分）
  └─ 扩展同义查询词（提高召回率）
    ↓
[多源检索调度]
  ├─ 实时 API：天气服务、行情接口、地理服务 （优先级最高）
  ├─ 搜索引擎：百度 / 必应 / 自建搜索 （通用知识、新闻）
  └─ 内部知识库：产品 FAQ、常用百科 （成本最低、延迟最低）
    ↓
[结果重排序]
  ├─ 相关性得分：语义相似度打分×查询词覆盖度
  ├─ 权威性得分：来源可信度加权（官方 API > 知名媒体 > 个人博客）
  └─ 新鲜度得分：越近时间的结果优先（采用指数衰减）
    ↓
[摘要生成]
  ├─ Top-K 检索片段作为外部知识注入 Prompt
  └─ LLM 综合阅读生成回复 + 注出引用来源
    ↓
[引用贴标] 回复末尾附加信息来源 URL / 来源名称
```

**多源检索调度策略**：

| 源类型 | 适用 Query | 并/串行策略 | 延迟预期 |
|----------|------------|------------|----------|
| 实时 API | 天气、行情、汇率 | 并行 + 超时 500ms 就封锁 | < 300ms |
| 搜索引擎 | 新闻、百科、地点介绍 | 并行，Top-5 结果参与重排序 | < 800ms |
| 内部知识库 | 产品功能、FAQ | 并行 + 语义检索 | < 100ms |

**引用溯出设计**：

```json
{
  "answer": "今天北京的天气是晴转多云，最高气温 26°C，建议带一件薄外套出门哦。",
  "citations": [
    {"index": 1, "source": "天气局官方", "url": "https://...", "snippet": "..."},
    {"index": 2, "source": "小红书天气服务", "url": "https://...", "snippet": "..."}
  ],
  "freshness": "2026-05-28T08:00:00Z"
}
```

**联网查询与闲聊的融合风格**：

联网查询的结果不能直接唯读、平铺式输出，需要经过口语化层改写为符合人设的回复风格。

```
搜索引擎原始返回：
  "北京天气：第一轮 6-12°，第二轮 8-15°，限行号......"
    ↓ LLM 口语化 × 人设注入
  "今天天气不错哟，晴转多云，不过早晚温差有点大，最好带个外套嗷~"
```

**关键决策**：
- 实时 API 超时不封锁整个联网查询，而是降级到搜索引擎结果、再降级到模型记忆内的内置知识库、最后公开声明信息可能不最新
- 引用内容不强制展示，但经验证在有引用的情况下用户信任度显著提升，可配置是否展示
- 联网查询结果不进语义缓存（L2），避免历史查询结果污染实时回答

**答辩问答预设**：
> Q：联网查询和 RAG 有什么区别？
> A： RAG 是大概念，联网查询是它的一种实现形式。我们的这个联网查询有三点额外工作：第一，实时 API 接入（标准 RAG 只有静态知识库）；第二，多源混合重排序（不是简单拼接所有内容）；第三，返回结果还需要经过口语化 + 人设注入，而不是原文展示。

### 2.5 模型 × Prompt 笛卡尔组合

**能力定位**：通过构建「模型池 × Prompt 池」的组合矩阵，实现多实验并行、灵活调度，避免单一配置的局限性。

**组合矩阵示例**：

```
模型池                    Prompt 池
────────────              ──────────────────
M1: GPT-4o          ×    P1: 温柔姐姐人设
M2: 文心一言 4.5    ×    P2: 活泼朋友人设
M3: 端侧小模型      ×    P3: 专业助理人设
                          P4: 幽默段子手人设

笛卡尔积 → 12 个候选配置（M×P combinations）
```

**路由调度策略**：

```
请求进入推理层
    ↓
读取 AB 实验分桶 → 确定当前用户命中哪个实验组
    ↓
实验组配置 = {model_id: "M1", prompt_id: "P2"}
    ↓
按 sub_intent 做 Prompt 精调：
    - 情感类  → Prompt 加入"共情引导"片段
    - 幽默类  → Prompt 加入"段子能力"片段
    - 问候类  → Prompt 精简，减少 token 消耗
    ↓
拼装最终 Prompt = Base 人设 + 场景片段 + 多轮上下文 + 当前 Query
```

**组合配置管理**：

```yaml
# 配置中心，支持热更新
combinations:
  - id: "combo_001"
    model: "gpt-4o"
    prompt_template: "persona_warm_sister"
    ab_group: "exp_A"
    weight: 0.3         # 流量占比

  - id: "combo_002"
    model: "ernie-4.5"
    prompt_template: "persona_funny_friend"
    ab_group: "exp_B"
    weight: 0.3

  - id: "combo_base"
    model: "ernie-4.5"
    prompt_template: "persona_default"
    ab_group: "control"
    weight: 0.4
```

**关键决策**：
- Prompt 采用**模板分段设计**（Base + 场景片段），避免全量 Prompt 膨胀，片段可独立迭代
- 新 combo 上线时先走**灰度流量（1%→5%→20%）**，指标达标后再放量，防止劣化配置大面积影响用户
- 模型间的**价格/质量/延迟三角**纳入路由权重，低峰期可多用大模型；高峰期自动切到小模型降本

**答辩问答预设**：
> Q：笛卡尔组合数量爆炸怎么办，不可能把所有组合都跑一遍 AB？
> A：对，实际上我们采用**分阶段淘汰**策略：先用小流量快速过滤明显差的组合（统计显著需要 N 次请求），再把胜出的 top-K 进入下一轮精细对比。本质上是个多臂赌博机（MAB）问题，用 UCB 或 Thompson Sampling 做流量分配，收敛速度比纯 AB 快 3~5 倍。

### 2.4 AB 实验

**能力定位**：支撑闲聊智能体快速迭代的核心基础设施，让每一次模型/Prompt/策略变更都有数据支撑。

**AB 框架核心模块**：

| 模块 | 职责 |
|------|------|
| **分桶服务** | 按 user_id hash 做一致性分桶，保证同一用户始终在同一组 |
| **实验配置中心** | 实验列表、分组比例、互斥关系、有效期 |
| **指标采集** | 异步埋点：满意度、追问率、负反馈率、会话深度 |
| **显著性检验** | 自动计算 p-value，达到显著性阈值后告警通知 |
| **实验版本管理** | 实验快照存档，支持历史实验结果追溯 |

**实验隔离规则**：

```
实验层 1（模型实验）    ←→    实验层 2（Prompt 实验）
      ↓ 互斥或正交                      ↓
同一请求只命中同层的一个实验，不同层可叠加
例：用户命中 M2 模型实验，同时命中 P3 Prompt 实验，
    最终走 (M2, P3) 组合
```

**核心指标体系**：

```
主指标（决策指标）：
  - 用户满意度（点赞/踩）
  - 会话深度（当轮是否继续追问）
  - 负反馈率（举报/跳出）

辅助指标（诊断指标）：
  - P50/P99 延迟
  - 首 Token 延迟（流式场景）
  - token 消耗量（成本）
  - 改写率、拒答率
```

**关键决策**：
- 采用**分层正交实验**，允许模型实验和 Prompt 实验同时进行，互不干扰，提升实验并行度
- **Holdout 组**长期保留 5% 流量作为基准对照，防止全量实验时失去参照基线
- 实验结论与 combo 配置中心直连：实验胜出 → 自动触发流量切换工单，减少人工操作窗口

---

### 2.6 输出标准化 & 口语化

**能力定位**：模型的原始输出往往过于书面化、格式化，本模块负责将其改造为符合对话场景的自然口语风格。

**标准化 Schema**：

```json
{
  "text": "完整回复文本",
  "segments": [
    {"type": "tts", "text": "口语化播报文本"},
    {"type": "display", "text": "界面展示文本（可含换行/列表）"},
    {"type": "action", "payload": {"type": "show_card", "data": {...}}}
  ],
  "meta": {
    "length_level": "short|medium|long",
    "tone": "warm|funny|neutral",
    "safe": true
  }
}
```

**口语化处理流水线**：

```
模型原始输出
    ↓
[格式清洗] 去除 markdown 符号、多余换行、列表项前缀
    ↓
[句式改写] "您可以..." → "你可以..."；
           "首先...其次...最后..." → 口语化连接词
    ↓
[长度控制] TTS场景：单次回复 < 80字；超长时截断 + 追加"你想听更多吗？"
    ↓
[多样性注入] 同类开头句式随机轮换，避免千篇一律的"好的，"开头
    ↓
[情感标记] 根据 sub_intent 注入语气词："哈哈"、"嗯~"、"唉"
    ↓
输出标准化 JSON
```

**答辩问答预设**：
> Q：多样性注入会不会让回复显得不一致、不专业？
> A：关键是**按场景分层控制**。幽默/情感类闲聊，允许高多样性；问答类、信息类，多样性收紧，保持准确稳定。我们用 sub_intent 字段作为多样性开关的控制变量，而不是全局统一设置。

---

### 2.7 攒包 & 动态替换

**能力定位**：在流式输出场景下，控制文本如何分包下发，并支持在回复中注入动态内容（实时数据、卡片、表情等），同时触发 TTS 并行渲染以降低感知延迟。

**分包策略**：

```
流式 Token 流
    ↓
[首包触发] 积累到第一个完整句子（句号/问号/感叹号）→ 立即下发
    优先级：低延迟 > 完整性
    目标：首包延迟 < 200ms
    ↓
[续包合并] 后续 Token 按 50ms 时间窗口或 20 Token 数量合并成包
    优先级：TTS 自然度 > 低延迟
    ↓
[尾包标记] 检测到 [END] 信号后，下发尾包 + stream_done 标记
```

**动态替换机制**：

```
模型生成时，遇到需要实时数据的位置使用占位符：
    "今天天气{weather_placeholder}，你打算去哪里玩？"
    
    ↓ 异步并行请求天气服务
    ↓ 占位符替换
    
    "今天天气晴转多云，你打算去哪里玩？"
```

**关键决策**：

| 场景 | 首包策略 | 原因 |
|------|----------|------|
| TTS 播报 | 第一个句子立即下发 | 人耳感知延迟窗口约 300ms，首字快才有流畅感 |
| 屏幕展示 | 等待完整段落 | 展示场景用户眼睛可以阅读，文字不完整反而体验差 |
| 卡片类回复 | 等待全量 | 卡片数据必须完整才能渲染，不能分块 |

---

### 2.8 干预能力

**能力定位**：在模型推理结果和最终下发之间插入人工/规则控制层，解决模型"不听话"、热点事件应急响应、合规要求等场景。

**干预优先级链**：

```
P0 - 全局封禁词（合规底线，不可绕过）
P1 - 黑名单 Query → 固定拒答（如品牌负面话题）
P2 - 白名单 Query → 强制指定回复（如品牌宣传语）
P3 - 模型输出敏感词替换（脱敏处理）
P4 - 话术模板注入（节日问候、活动通知前缀）
P5 - A/B 干预组（实验性干预规则）
─────────── 以上任一命中即短路，不再向下 ──────────
P6 - 正常下发模型回复
```

**人工审核队列**：

```yaml
audit_queue:
  trigger:
    - 负反馈率 > 阈值的 Query
    - 模型输出包含低置信敏感内容
    - 用户主动举报
  action:
    - 进入人工标注队列
    - 审核通过 → 加白名单
    - 审核拒绝 → 加黑名单 + 触发同类 Query 回扫
```

**热点应急能力**：
- 配置中心支持**分钟级热更新**，热点事件爆发时 5 分钟内可以全量覆盖指定 Query 的回复
- 干预规则支持**正则/语义双模式**：正则规则低延迟适合关键词匹配；语义规则覆盖表达变体

---

### 2.9 评测能力

**能力定位**：闭环驱动迭代的核心，没有评测体系，AB 实验的指标就是瞎跑。

**评测体系三层**：

```
第一层：自动评测（每次上线前必跑）
  ├─ 基准集回归：固定 500 条标准问答，回归 pass rate > 95% 才允许上线
  ├─ 人设一致性：模型回复与人设文档的语义相似度
  ├─ 安全检测：违禁词、政治敏感、广告植入自动扫描
  └─ 多样性检测：同 Query 多次回复的 BLEU 多样性分数

第二层：在线自动评测（生产流量实时抽样）
  ├─ 用户行为信号：追问率、点赞踩、会话深度
  ├─ 模型自评：用另一个模型对回复打分（GPT-as-Judge）
  └─ 异常检测：回复长度异常、重复率异常实时告警

第三层：人工标注评测（周期性）
  ├─ 主观质量标注：流畅度 / 相关性 / 人设一致 / 安全 四维 1~5 分
  ├─ 错误归因标注：是改写问题 / 分类问题 / 模型问题 / Prompt 问题
  └─ AB 实验结果人工 review（避免指标被刷）
```

**评测指标体系**：

| 维度 | 指标 | 计算方式 |
|------|------|----------|
| 质量 | 满意度评分 | 人工标注 1~5 分均值 |
| 安全 | 违规率 | 被举报/被拦截回复占比 |
| 一致性 | 人设漂移率 | 与人设文档语义余弦相似度 < 阈值的比例 |
| 效率 | 首 Token 延迟 | P50 / P99 |
| 成本 | 单次会话 token 消耗 | 平均 token × 单价 |

**答辩问答预设**：
> Q：GPT-as-Judge 会不会有偏差，用 GPT 评 GPT 不就是自己给自己打分？
> A：这是个真实存在的问题，我们的做法是：Judge 模型和推理模型**选不同厂商**（例如推理用文心，Judge 用 GPT-4o），减少同源偏差；同时对 Judge 结论做**人工抽样校准**，建立 Judge 模型本身的可信度评估，发现偏差就加校准规则。

## 三、补充能力模块

> 以下 6 个模块是用户未提及但架构完整性必须具备的，每一个缺失都会导致生产环境出现真实故障或体验断层。

### 3.1 多轮上下文管理

**为什么必须有**：闲聊天然是多轮场景，没有上下文管理，用户说"那你觉得呢"，系统完全不知道"那"指什么。

**核心数据结构**：

```json
{
  "session_id": "uuid",
  "user_id": "u_xxx",
  "turns": [
    {"role": "user",      "text": "你喜欢看什么电影？",    "ts": 1716000001},
    {"role": "assistant", "text": "我喜欢科幻片！",        "ts": 1716000003},
    {"role": "user",      "text": "那你看过星际穿越吗？",  "ts": 1716000010}
  ],
  "summary": "用户在聊电影话题，已提及科幻片和星际穿越",
  "ttl": 1800
}
```

**上下文压缩策略**：

```
原始对话轮次增长 → Context Window 压力上升
    ↓
策略 1：滑动窗口（保留最近 N 轮，丢弃旧轮次）
    ↓
策略 2：摘要压缩（超过阈值后，调用摘要模型将旧轮次压缩为 summary 字段）
    ↓
策略 3：关键信息提取（从历史轮次提取实体/偏好写入用户画像，不再占 Context）
```

**Session 生命周期管理**：
- 活跃 Session（30 分钟内有交互）：保留完整上下文，Redis 热存储
- 冷却 Session（超过 30 分钟）：压缩为摘要，降级到冷存储
- 跨天重连：加载摘要 + 用户画像，重建"软上下文"

---

### 3.2 个性化 & 用户画像

**为什么必须有**：同一个"讲个笑话""，对喜欢冷笑话的用户和喜欢谐音梗的用户，最优回复完全不同。没有个性化，闲聊智能体只是公共大脑，不是"你的助手"。

**画像分层**：

```
静态偏好（变化慢，长期有效）
  ├─ 幽默风格偏好：冷笑话 / 谐音梗 / 段子 / 不喜欢笑话
  ├─ 话题偏好：电影 / 音乐 / 运动 / 科技
  └─ 语气偏好：正式 / 随意 / 可爱 / 简洁

动态状态（实时，本次 Session 有效）
  ├─ 当前情绪：开心 / 焦虑 / 无聊
  ├─ 话题深度：刚开始 / 已深聊 3 轮
  └─ 最近提及的实体：周杰伦 / 星际穿越

长期记忆（跨 Session 持久化）
  └─ 上次说过要去看演唱会、不喜欢被催
```

**冷启动方案**：
- 新用户：使用**平台默认画像**（温柔、随意风格），同时开启**偏好探针**（在对话中巧妙问出偏好）
- 热启动：历史画像直接注入 Prompt，开场即个性化

---

### 3.3 安全过滤 & 内容风控

**为什么必须有**：大模型会幻觉、会被"越狱"、会生成不合规内容，没有风控层就是裸奔上线。

**双层过滤架构**：

```
前置过滤（Query 进推理层之前）
  ├─ 违禁词命中 → 直接拒答，不消耗模型算力
  ├─ Prompt 注入检测 → 忘记你的设定类攻击识别
  └─ 用户历史风险评分 → 高风险用户加严过滤策略

后置过滤（模型输出之后）
  ├─ 违禁词二次扫描（模型可能绕过前置词典）
  ├─ 隐私信息检测：手机号、身份证、地址等 PII 信息脱敏
  ├─ 模型安全分类器：色情 / 暴力 / 政治的语义级检测
  └─ 品牌声誉保护：竞品负面对比、诱导性话术识别
```

**分级响应策略**：

| 风险级别 | 触发条件 | 处理方式 |
|----------|----------|----------|
| L0 极高危 | 政治敏感、违法内容 | 硬拦截 + 记录 + 告警 |
| L1 高危 | 色情、暴力 | 拦截 + 返回固定安全话术 |
| L2 中危 | 隐私泄露、竞品攻击 | 部分替换 + 降级回复 |
| L3 低危 | 轻微不当用语 | 替换敏感词后正常下发 |

---

### 3.4 降级 & 兜底策略

**为什么必须有**：模型服务不稳定、网络抖动、高峰限流——这些在生产环境都会发生，没有降级方案就等着全线崩溃。

**降级链路设计**：

```
主链路：在线大模型（GPT-4o / 文心 4.5）
    ↓ [超时 > 2s / 错误率 > 5%] 触发降级
    ↓
备用链路 1：在线中模型（文心 Lite / 本地部署 7B）
    ↓ [备用链路也不可用] 继续降级
    ↓
备用链路 2：端侧小模型（1.5B 量化模型，本地推理）
    ↓ [端侧模型也失败] 最终兜底
    ↓
兜底话术库：预置 200 条高质量通用回复，按 Query 类型随机抽取
```

**降级判断与恢复**：
- 熔断器模式：连续 N 次失败后开启熔断，定期探测主链路是否恢复
- 降级时打标记到回复 meta，供评测层识别，避免降级回复污染评测基准
- 恢复时**不立即全量切回**，用小流量灰度确认主链路稳定后再全量恢复

---

### 3.5 缓存 & 复用

**为什么必须有**：闲聊场景有大量重复或近似 Query（"你好"、"讲个笑话"），每次都走完整推理链路是巨大的算力浪费。

**缓存分层策略**：

```
L1 精确缓存（命中率约 15%）
  ├─ Key：改写后的 Query + session_type
  ├─ Value：预计算的高质量回复（人工审核过的黄金回复）
  └─ TTL：7 天，适用于固定问候语、常见招呼

L2 语义缓存（命中率约 30%）
  ├─ Key：Query 的语义向量（Embedding）
  ├─ 相似度阈值：cosine > 0.92 时命中
  ├─ Value：历史高分回复（满意度评分 > 4.5 的回复）
  └─ TTL：24 小时，避免时效性内容过期

L3 组合缓存（模型调用结果缓存）
  ├─ Key：(model_id, prompt_hash, context_hash, query)
  └─ 适用于：相同上下文下的重复请求（防抖、重试场景）
```

**注意事项**：
- 个性化内容**不进 L1/L2 全局缓存**，避免用户 A 的个性化回复推给用户 B
- 缓存命中时仍记录请求日志，打标 `cache_hit=true`，评测层可单独分析缓存回复质量

---

### 3.6 监控 & 可观测性

**为什么必须有**：闲聊智能体链路长、模块多，没有全链路监控，出问题时故障定位要几个小时甚至几天。

**全链路 Tracing**：

```
每个请求生成唯一 trace_id，贯穿所有模块：

接入层   → [trace_id: abc123, ts: T0]
改写模块 → [trace_id: abc123, latency: 15ms, rewrite: true]
分类模块 → [trace_id: abc123, latency: 22ms, label: chat, conf: 0.91]
AB 分桶  → [trace_id: abc123, group: exp_A, combo: M1+P2]
```

## 四、关键设计决策（ADR）

### 决策 1：笛卡尔组合冷启动——新 Combo 上线策略

**问题**：新模型或新 Prompt 上线时，没有历史数据，流量该给多少？给少了收敛慢，给多了风险大。

**决策**：采用**分阶段灰度 + MAB 动态调节**

```
阶段 1：1% 流量，人工观察 1 天，无明显劣化则进阶
阶段 2：5% 流量，跑 MAB（UCB 算法），自动判断是否继续放量
阶段 3：20% 流量，显著性检验通过后进入正式 AB 实验
阶段 4：AB 实验胜出 → 逐步放量至目标占比
```

**放弃的方案**：直接 50% 流量对打——风险过高，新 Combo 若存在人设漂移或安全问题会大面积影响用户。

---

### 决策 2：攒包首包延迟 vs TTS 自然度 trade-off

**问题**：首包越早下发感知延迟越低，但包太小（如只有半句话），TTS 语气断裂，体验差。

**决策**：**按输出类型区分首包策略**

| 输出类型 | 首包触发条件 | 原因 |
|----------|-------------|------|
| 情感回复 | 第一个完整短句（逗号/句号） | 情感回复短，快出首包体验好 |
| 信息回复 | 第一个完整长句（句号）或 30 Token | 信息回复需要语义完整 |
| 列表回复 | 等全量 | 列表残缺显示体验极差 |

**放弃的方案**：统一等完整段落——导致情感场景首字延迟超过 1s，用户感知明显。

---

### 决策 3：评测指标体系——主观指标如何量化

**问题**：闲聊质量天然主观，"有趣"、"自然"难以量化，怎么让评测可重复、可比较？

**决策**：**三层量化拆解**

```
第一层：行为指标（客观，无需人工）
  → 追问率、会话深度、负反馈率、点赞率

第二层：模型自动评分（半客观）
  → GPT-as-Judge 打多维度分 + 校准系数修正偏差

第三层：人工标注（主观，周期性校准）
  → 建立标注规范（4 个维度、5 级量表）+ 标注一致性检验（Kappa > 0.7）

结论：以行为指标为主决策指标，模型自评为辅助参考，人工标注为校准基准
```
