# 02 POI 数据与检索

## 总览：POI 是 LBS 业务的核心资产

POI（Point of Interest）可以理解为“地图上有业务意义的地点”。餐厅、便利店、医院、学校、地铁站、停车场、充电桩、写字楼、景区、仓库、驿站都可以是 POI。

对 0 基础后端来说，POI 这一节要抓住两个关键词：数据质量和检索排序。

POI 不只是一个点，它是一份持续变化的业务数据。一个门店可能会搬迁、停业、改名、换电话、改营业时间；一个商场可能有多个入口和楼层；同一家店可能被多个数据源重复采集。后端要做的不只是存储 POI，还要支持搜索、附近查询、去重、更新、审核、排序和问题排查。

面试中，POI 通常会和搜索、推荐、导航、配送、本地生活结合起来问。你需要能说明：

- POI 有哪些字段。
- POI 数据从哪里来。
- 为什么 POI 数据会不准。
- 关键词搜索和附近搜索怎么做。
- 搜索结果为什么不能只按距离排序。

## 分解一：POI 的数据模型

一个较完整的 POI 通常包含四类信息：基础信息、空间信息、业务信息、质量信息。

### 基础信息

基础信息用于描述这个地点是什么。

常见字段：

```text
poi_id
name
alias
address
phone
category_id
category_name
brand_id
brand_name
status
source
created_at
updated_at
```

说明：

- `name` 是主名称，例如“星巴克 北京西站店”。
- `alias` 是别名，例如“KFC”对应“肯德基”。
- `category` 表示类目，例如餐饮、酒店、交通设施。
- `brand` 表示品牌，例如麦当劳、瑞幸咖啡。
- `status` 表示营业中、停业、关闭、待审核。

### 空间信息

空间信息用于描述这个地点在哪里。

常见字段：

```text
longitude
latitude
coord_type
province_code
city_code
district_code
street
aoi_id
floor
entrance_points
parking_points
```

重点理解：

- POI 中心点不一定适合导航。
- 大型商场、医院、园区需要入口点。
- 地下停车场、上车点、配送点可能需要单独建模。
- 楼层信息对室内场景很重要。

### 业务信息

业务信息用于描述这个地点能提供什么服务。

例如：

- 营业时间。
- 是否支持配送。
- 配送范围。
- 是否可预约。
- 是否可停车。
- 用户评分。
- 热度。
- 图片。
- 标签。

这些字段会影响搜索排序、筛选和推荐。

### 质量信息

质量信息用于判断这个 POI 是否可信。

例如：

- 数据来源可信度。
- 最近更新时间。
- 人工审核状态。
- 用户纠错次数。
- 坐标置信度。
- 地址完整度。
- 是否疑似重复。

面试中可以强调：POI 是动态资产，质量治理比一次性入库更重要。

## 分解二：POI 数据从哪里来

常见来源包括：

- 地图数据供应商。
- 第三方商户库。
- 商家入驻。
- 运营人员采编。
- 用户纠错和反馈。
- 订单、轨迹、支付、核销等业务行为挖掘。
- 公开数据或合作方数据。

多来源带来的问题：

- 同一家店被重复录入。
- 名称、电话、地址不一致。
- 坐标有偏差。
- 状态更新不同步。
- 分类体系不同。

后端需要做数据融合。常见思路是基于名称相似度、地址相似度、电话一致性、品牌、空间距离、类目等特征判断是否为同一 POI。

## 分解三：POI 数据质量问题

### 重复 POI

同一家店出现多个结果，会导致：

- 用户不知道选哪个。
- 点击和热度被分散。
- 导航和下单地址不一致。
- 运营统计不准确。

处理方法：

- 电话一致可强匹配。
- 名称相似、距离很近、类目一致可疑似重复。
- 品牌店结合门店编号。
- 人工审核高风险合并。

### 坐标错误

坐标错误会导致：

- 地图展示位置不对。
- 用户导航到错地方。
- 配送和到店判断失败。
- 附近搜索排序异常。

排查思路：

- 检查坐标系。
- 检查经纬度顺序。
- 对比地址解析结果。
- 对比用户轨迹和到店行为。
- 检查入口点和中心点是否混用。

### 状态滞后

店铺关闭但仍展示，或者新店开业但搜不到，都会影响用户体验。

治理方法：

- 商户后台主动更新。
- 订单和核销行为验证。
- 用户反馈。
- 周期性巡检。
- 第三方数据同步。

### 分类错误

分类会影响召回和排序。比如把“充电站”标成“停车场”，用户搜充电桩时就可能搜不到。

治理方法：

- 类目规则校验。
- 名称关键词识别。
- 商家自选类目审核。
- 用户行为反推。
- 模型分类。

## 分解四：POI 检索链路

POI 检索可以拆成召回、过滤、排序、展示四步。

### 召回

召回是先找出可能相关的候选 POI。

常见召回方式：

- 关键词倒排索引。
- 拼音和首字母索引。
- 同义词和别名召回。
- 类目召回。
- 空间索引召回附近 POI。
- 热门 POI 召回。

例如用户搜“kfc”，系统应该能召回“肯德基”；用户搜“咖啡”，系统应该召回咖啡店类目，而不只是名称包含咖啡的 POI。

### 过滤

过滤用于剔除不符合业务条件的 POI。

常见过滤条件：

- 城市。
- 距离半径。
- 类目。
- 营业状态。
- 是否支持当前业务。
- 风控状态。
- 用户权限。

### 排序

排序决定结果展示顺序。

常见排序因素：

- 文本相关性。
- 距离。
- 热度。
- 评分。
- 营业状态。
- 品牌权重。
- 用户历史偏好。
- 是否可服务。
- 数据质量。

重点：不能只按距离排序。用户搜“北京大学”时，最相关的北京大学应该优先，而不是离用户最近的“北京大学某门店广告牌”。用户搜“咖啡”时，距离更重要；用户搜具体店名时，文本相关性更重要。

### 展示

展示结果要给用户足够判断信息：

- 名称。
- 地址。
- 距离。
- 类目。
- 营业状态。
- 评分。
- 标签。
- 地图点位。

如果候选有歧义，可以展示城市、区县、商圈帮助用户选择。

## 后端开发视角：POI 服务怎么设计

### 存储设计

常见存储组合：

- 关系型数据库：存主数据和管理字段。
- Elasticsearch：做关键词检索、拼音、别名、相关性排序。
- Redis：缓存热门 POI、城市类目、品牌词典。
- 空间数据库或空间索引：做附近查询、区域过滤。

### 索引设计

需要考虑：

- 名称索引。
- 别名索引。
- 地址索引。
- 类目索引。
- 品牌索引。
- 城市索引。
- 经纬度空间索引。
- 状态索引。

### 接口示例

```json
{
  "keyword": "星巴克",
  "longitude": 116.3,
  "latitude": 39.9,
  "coordType": "GCJ02",
  "cityCode": "110000",
  "radius": 5000,
  "category": "coffee",
  "page": 1,
  "pageSize": 20
}
```

响应要尽量包含：

```json
{
  "poiId": "p123",
  "name": "星巴克 中关村店",
  "address": "北京市海淀区...",
  "longitude": 116.3,
  "latitude": 39.9,
  "distance": 320,
  "category": "咖啡店",
  "status": "营业中",
  "confidence": 0.96
}
```

### 异常和降级

常见降级策略：

- 定位不可用时使用城市中心或用户选择城市。
- 搜索无结果时放宽半径或启用纠错。
- ES 不可用时返回热门 POI 或缓存结果。
- 数据状态不确定时降低排序权重。

## 面试高频问题

### 问：POI 搜索为什么不能只按距离排序？

答题思路：

- 搜索意图不同，具体地点搜索更看重文本相关性。
- 类目搜索更看重距离、热度和可服务状态。
- 还要考虑营业状态、品牌、评分、数据质量。
- 排序通常是多因素综合。

### 问：如何做 POI 去重？

答题思路：

- 电话、品牌门店号可以做强特征。
- 名称相似、地址相似、距离近、类目一致可以做弱特征。
- 多特征打分判断疑似重复。
- 高风险合并需要人工审核或灰度。

### 问：用户反馈 POI 位置错误，如何排查？

答题思路：

- 查坐标系和经纬度顺序。
- 对比地址解析和第三方地图。
- 看用户导航、到店、订单轨迹。
- 判断中心点和入口点是否混用。
- 修正后更新索引和缓存。

## 本节总结：面试突击记忆清单

- POI 是有业务含义的位置点，不只是经纬度。
- POI 数据模型包括基础信息、空间信息、业务信息、质量信息。
- POI 检索链路是召回、过滤、排序、展示。
- 排序要综合文本相关性、距离、热度、状态、业务规则和数据质量。
- POI 数据治理重点是去重、纠偏、分类、状态更新和多源融合。
- 后端要关注存储、索引、缓存、坐标系和异常降级。

能讲清一个“附近搜索”服务，你就已经覆盖了 POI 面试的大部分基础盘。
