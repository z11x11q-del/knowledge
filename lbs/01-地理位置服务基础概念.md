# 01 地理位置服务基础概念

## 总览：0 基础后端先建立一张 LBS 地图

LBS（Location Based Services）可以理解为“围绕位置做查询、计算、展示和决策的一整套服务”。对后端开发来说，LBS 不是简单调用地图 SDK，也不是只会存经纬度。它更像一套空间数据服务体系：用户、车辆、骑手、门店、道路、行政区、配送区、轨迹，这些对象都带有地理位置或空间形状，后端要负责把它们存好、查快、算准、对业务解释清楚。

如果你是 0 基础后端，突击 LBS 岗位时先抓住一句话：LBS 的核心是把“现实世界的位置关系”转换成“系统可以计算的点、线、面、路网和索引”。

面试中这一节常被用来判断你是否真的理解地图业务：

- 你是否知道定位、地图展示、路线规划、地理编码不是一回事。
- 你是否知道经纬度有坐标系，坐标系错了会整体偏移。
- 你是否知道“附近 3 公里”不一定等于真实可达 3 公里。
- 你是否能从后端角度讲清一个 LBS 请求从输入到输出经历了什么。

## 分解一：LBS 到底包含哪些能力

LBS 能力可以按“输入是什么、输出是什么”来理解。

### 定位

定位的输入通常来自客户端、设备或车载终端，输出是一个带精度和时间戳的位置点。

典型输出：

- 经度、纬度。
- 定位时间。
- 定位来源，如 GPS、Wi-Fi、基站。
- 精度半径。
- 速度和方向。

后端不能只相信经纬度，还要判断它是否过期、是否漂移、精度是否足够。

### 地理编码

地理编码把文本地址转换成坐标。

例如：

```text
输入：北京市海淀区中关村软件园二期
输出：经纬度、标准化地址、行政区、匹配精度、置信度
```

它解决的是“地址文字如何变成系统可计算的位置”。

### 逆地理编码

逆地理编码把坐标转换成可读地址。

例如：

```text
输入：经纬度
输出：北京市海淀区某道路附近、最近 POI、所属小区或商圈
```

它解决的是“这个点在现实世界中应该被描述成什么地方”。

### POI 检索

POI 是 Point of Interest，表示有业务意义的地点，例如门店、学校、医院、车站、停车场。

POI 检索解决：

- 搜某个店在哪里。
- 查当前位置附近有什么。
- 根据分类找附近充电桩、便利店、停车场。

### 路线规划

路线规划根据起点、终点和交通方式，在路网中计算可行路径。

它输出的不只是路线线条，还包括：

- 总距离。
- 预计耗时。
- 路段列表。
- 转向动作。
- 收费信息。
- 备选路线。

### 导航

导航是在路线规划基础上，结合实时定位持续引导用户。路线规划偏服务端计算，导航更强调端云协同和实时状态。

导航要解决：

- 用户当前在路线哪一段。
- 什么时候播报。
- 是否偏航。
- 是否需要重算。
- 是否到达终点。

### 地理围栏

地理围栏判断某个对象是否进入、离开或停留在某个区域内。

例如：

- 骑手是否进入门店 100 米范围。
- 用户地址是否在配送范围内。
- 车辆是否进入禁停区。

### 地图匹配

地图匹配把 GPS 点或轨迹吸附到真实道路上。

它解决的是“定位点不准，但业务要知道用户到底在哪条路上”。

## 分解二：位置数据的基本形态

LBS 后端最常处理的是点、线、面。

### 点 Point

点是最基础的空间对象。

常见点对象：

- 用户当前位置。
- 门店位置。
- 司机位置。
- 骑手位置。
- 站点位置。
- 设备位置。

后端常见字段：

```text
id
longitude
latitude
coord_type
accuracy
timestamp
source
business_type
```

注意，经纬度字段最好明确命名，不要只写 `x`、`y`。很多线上事故来自经纬度顺序写反。

### 线 LineString

线表示由多个点连成的路径。

常见线对象：

- 道路。
- 导航路线。
- 用户轨迹。
- 公交线路。
- 物流运输线路。

线对象适合计算长度、相交、是否经过某区域、轨迹是否偏离路线。

### 面 Polygon

面表示一个封闭区域。

常见面对象：

- 行政区。
- 商圈。
- 小区边界。
- 配送范围。
- 禁行区。
- 园区。

面对象常用于点面判断，例如“点是否在多边形内”。

## 分解三：坐标系是 LBS 的第一道坑

后端面试很喜欢问坐标系，因为这是最基础、也最容易出线上问题的知识点。

### 常见坐标系

- WGS84：GPS 原始坐标常用坐标系，全球通用。
- GCJ-02：国内常见互联网地图坐标系，也叫火星坐标系。
- BD-09：百度地图坐标系，在 GCJ-02 基础上再次偏移。

### 为什么会偏移

如果服务端存的是 WGS84，但前端用高德或腾讯地图按 GCJ-02 展示，就可能出现点位整体偏移。这个偏移不是几米级小误差，在城市中可能足以让门店出现在马路对面甚至楼外。

### 后端要做什么

后端需要在系统层面明确：

- 数据库存储统一使用哪种坐标系。
- 对外接口输入支持哪些坐标系。
- 返回给不同地图 SDK 时是否需要转换。
- 日志和排查工具展示的坐标系是什么。
- 批处理和实时服务是否使用同一套转换规则。

面试回答可以这样说：坐标系要在系统边界处标准化，内部尽量统一存储和计算；对接外部地图或第三方数据时，在接入层或适配层完成转换，并保留坐标来源。

## 分解四：距离不是一个概念

后端做 LBS 时，不要看到两个经纬度就直接用欧式距离。

常见距离口径：

- 直线距离：两个点之间的空间距离，适合附近粗筛。
- 球面距离：考虑地球曲率的直线距离，常用 Haversine 公式。
- 投影距离：投影到平面后的距离，适合局部空间计算。
- 路网距离：沿真实道路走的距离。
- 时间距离：考虑速度、拥堵、红绿灯后的出行成本。

业务选择不同，距离口径不同：

- 附近搜索：可以先用直线距离召回，再排序。
- 外卖配送：更关注路网距离和配送时间。
- 网约车 ETA：更关注时间距离。
- 地理围栏：通常先做直线或点面判断。
- 计费：需要轨迹里程或路网里程，不能只看起终点直线距离。

## 分解五：地图层级和瓦片

互联网地图不是一次性加载全世界，而是按缩放层级切成瓦片。

你需要理解：

- Zoom 表示缩放层级，层级越大，细节越多。
- Tile 表示瓦片，地图按 `z/x/y` 组织。
- 栅格瓦片是图片，客户端显示简单。
- 矢量瓦片是数据，客户端按样式渲染。

后端为什么要懂瓦片：

- 业务点位可以按瓦片或网格加载，避免一次返回太多。
- 地图图层需要按缩放层级控制数据密度。
- 热力图、轨迹、围栏展示通常需要切片或聚合。
- 瓦片缓存会影响地图加载性能。

## 后端开发视角：一个 LBS 服务怎么设计

以“附近门店查询”为例，后端链路可以拆成：

1. 接收用户位置、城市、关键词、业务筛选条件。
2. 校验坐标系、经纬度合法性、定位精度和时间戳。
3. 用空间索引召回附近门店候选。
4. 用业务条件过滤，例如营业状态、配送能力、类目。
5. 计算距离或调用距离服务。
6. 综合距离、热度、相关性排序。
7. 返回门店列表、坐标、距离、展示字段。
8. 记录日志，用于效果分析和问题排查。

典型接口字段：

```json
{
  "longitude": 116.3,
  "latitude": 39.9,
  "coordType": "GCJ02",
  "cityCode": "110000",
  "keyword": "咖啡",
  "radius": 3000,
  "pageSize": 20
}
```

后端需要注意：

- 半径不能无限大，需要限制。
- 经纬度要校验范围。
- 坐标系要明确。
- 结果要有距离口径说明。
- 排序要可解释。
- 低精度定位要有降级策略。

## 面试高频问题

### 问：定位、地图匹配、路线规划、导航有什么区别？

答题思路：

- 定位回答“用户当前大概在哪里”。
- 地图匹配回答“用户更可能在哪条道路上”。
- 路线规划回答“从 A 到 B 应该怎么走”。
- 导航回答“用户沿路线行进时每一刻如何引导、是否偏航、是否到达”。

### 问：为什么两个点距离很近，但实际走过去很远？

答题思路：

- 直线距离没有考虑道路、河流、围墙、高架、入口。
- 实际出行依赖路网距离。
- 对配送、导航、网约车等场景，应使用路网距离或 ETA。

### 问：地图上点位偏了，怎么排查？

答题思路：

- 先确认经纬度顺序是否写反。
- 再确认坐标系是否一致。
- 检查数据库、接口、前端 SDK 的坐标类型。
- 检查是否做了重复转换或漏转换。
- 对比第三方地图拾取点和业务数据源。

## 本节总结：面试突击记忆清单

记住这几个核心句子：

- LBS 是围绕位置做查询、计算、展示和决策的服务体系。
- 后端处理的是点、线、面、路网、轨迹、围栏、索引这些可计算对象。
- 坐标系不统一会导致地图整体偏移。
- 直线距离、路网距离、ETA 不是同一个东西。
- 定位、地图匹配、路线规划、导航是四个不同问题。
- LBS 中台的价值是把通用位置能力沉淀成稳定、可复用、可观测的服务。

如果时间很短，至少要能讲清“一次附近搜索”或“一次导航请求”从输入到输出的完整链路，这是 LBS 面试的基本盘。
