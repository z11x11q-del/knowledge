# 03 地理编码与逆地理编码

## 总览：地址和坐标之间的双向翻译

地理编码（Geocoding）是把地址文本转换为经纬度，逆地理编码（Reverse Geocoding）是把经纬度转换为可读地址。它们是 LBS 后端最基础的能力之一。

对 0 基础后端来说，可以这样理解：

- 用户输入的是自然语言地址，系统需要把它变成可计算的位置。
- 客户端上传的是经纬度，业务需要知道它属于哪个城市、道路、小区或 POI。

地理编码解决“文字到坐标”，逆地理编码解决“坐标到文字”。这两个能力看似简单，实际难点在于地址不规范、同名地点多、数据源不一致、精度要求不同。

面试中这一节常用于判断你是否理解 LBS 数据链路：

- 如何解析一条自然语言地址。
- 如何处理地址歧义。
- 如何判断地理编码结果是否可信。
- 为什么低精度地址不能直接用于配送或导航。
- 逆地理编码为什么不是简单找最近 POI。

## 分解一：地理编码的输入和输出

### 输入

地理编码的输入通常是用户输入或业务系统传入的地址文本。

例如：

```text
北京市海淀区中关村软件园二期
上海市闵行区虹桥火车站出发层
广州市天河区体育西路地铁站 C 口
杭州余杭区梦想小镇 3 号楼
```

真实地址通常会有很多问题：

- 缺省城市。
- 省略区县。
- 错别字。
- 简称。
- 道路和 POI 混写。
- 楼栋、单元、楼层写法不统一。
- “附近”“对面”“东门”这类模糊描述。

### 输出

地理编码的输出不应该只有经纬度，还应包含结果质量。

典型输出：

```json
{
  "longitude": 116.30,
  "latitude": 39.98,
  "coordType": "GCJ02",
  "formattedAddress": "北京市海淀区中关村软件园二期",
  "province": "北京市",
  "city": "北京市",
  "district": "海淀区",
  "matchLevel": "AOI",
  "confidence": 0.92,
  "candidates": []
}
```

关键字段：

- `matchLevel` 表示匹配精度。
- `confidence` 表示置信度。
- `candidates` 用于多候选返回。
- `coordType` 明确坐标系。

## 分解二：地址解析

地址解析是把自由文本拆成结构化要素。

常见地址要素：

- 省。
- 市。
- 区县。
- 街道。
- 道路。
- 门牌号。
- 小区、园区、商场。
- 楼栋。
- 单元。
- 楼层。
- 房间号。
- 入口，如东门、南门、C 口。

例如：

```text
输入：北京市海淀区中关村软件园二期 8 号楼 3 层
解析：
城市：北京市
区县：海淀区
AOI：中关村软件园二期
楼栋：8 号楼
楼层：3 层
```

后端实现上，地址解析可能使用：

- 行政区划词典。
- 道路词典。
- POI 词典。
- 分词算法。
- 规则模板。
- 机器学习或序列标注模型。
- 同义词和别名库。

面试不一定要求你能写地址解析算法，但要能讲清它的目标：从不规范文本中提取可匹配的地址要素。

## 分解三：候选召回和匹配

解析完成后，系统要从地图数据中找可能匹配的对象。

### 候选类型

候选结果可能来自：

- POI。
- AOI，如小区、园区、商场。
- 道路。
- 门址。
- 行政区。
- 交叉路口。

例如用户输入“万达广场”，系统可能召回多个城市的万达广场；用户输入“人民路 88 号”，系统可能召回多个城市的人民路。

### 匹配因素

候选排序通常考虑：

- 文本相似度。
- 行政区一致性。
- 用户当前城市或定位。
- 道路和门牌是否匹配。
- POI 或 AOI 热度。
- 数据可信度。
- 地址层级完整度。

### 多候选处理

如果多个候选得分接近，就不应该强行返回一个结果。

常见策略：

- 返回候选列表让用户选择。
- 结合用户当前位置提高本地候选权重。
- 结合业务城市限制。
- 低置信度结果提示用户补充信息。
- 对配送等高风险业务要求二次确认。

## 分解四：结果精度等级

地理编码结果必须有精度等级。不同业务对精度要求不同。

常见等级：

- 门址级：具体到门牌或建筑入口。
- POI 级：具体到某个地点。
- AOI 级：具体到小区、园区、商场。
- 道路级：只知道在哪条路上。
- 区县级：只知道区县。
- 城市级：只知道城市。

业务使用建议：

- 外卖配送：至少 AOI 级，最好门址级或楼栋级。
- 网约车上车点：需要入口点或可达点。
- 天气服务：城市级即可。
- 风控统计：区县级可能足够。
- 导航：需要可到达的道路点或入口点。

面试回答要强调：不能只看是否返回经纬度，还要看匹配等级和置信度。

## 分解五：逆地理编码

逆地理编码输入是经纬度，输出是可读地址或空间上下文。

典型输出：

```json
{
  "province": "北京市",
  "city": "北京市",
  "district": "海淀区",
  "street": "东北旺西路",
  "nearestPoi": "中关村软件园",
  "aoi": "中关村软件园二期",
  "formattedAddress": "北京市海淀区东北旺西路中关村软件园二期附近"
}
```

逆地理编码不是简单找最近 POI，原因是：

- 最近 POI 不一定是用户所在地点。
- 点可能落在 AOI 内，应该优先返回所属区域。
- 点可能在道路上，应该返回道路和附近门牌。
- 点可能在商场内，需要楼层或入口上下文。
- 点可能在行政区边界附近，需要处理边界误差。

常见流程：

1. 根据坐标查行政区。
2. 查是否落在 AOI 或建筑面内。
3. 查附近道路和门牌。
4. 查附近 POI。
5. 按业务场景组合地址描述。

## 后端开发视角：地理编码服务怎么设计

### 服务接口

地理编码接口示例：

```json
{
  "address": "中关村软件园二期 8 号楼",
  "cityCode": "110000",
  "userLongitude": 116.3,
  "userLatitude": 39.9,
  "scene": "delivery"
}
```

逆地理编码接口示例：

```json
{
  "longitude": 116.3,
  "latitude": 39.9,
  "coordType": "GCJ02",
  "scene": "display"
}
```

### 存储和索引

常见索引：

- 行政区划树。
- 地址词典。
- POI 倒排索引。
- 道路和门址索引。
- AOI 空间索引。
- 别名和同义词索引。

技术组合：

- Elasticsearch 处理文本召回。
- 空间数据库处理点面关系。
- Redis 缓存热门地址和行政区。
- MySQL 或 PostgreSQL 存标准地址和结果。

### 置信度设计

置信度可以根据以下因素计算：

- 地址要素匹配完整度。
- 行政区是否一致。
- 文本相似度。
- 候选得分差距。
- 数据来源可信度。
- 结果精度等级。

低置信度结果应该有明确策略：

- 返回候选。
- 要求用户确认。
- 降级为低精度展示。
- 拒绝用于高风险业务。

## 典型业务场景

- 用户下单填写地址。
- 地图搜索地址。
- 网约车选择上车点。
- 物流解析收货地址。
- 风控判断用户所在城市。
- 运营统计订单行政区分布。
- 客服根据坐标定位用户位置。

## 常见问题和排查

### 地址解析错误

排查：

- 看解析出的行政区、道路、POI 是否正确。
- 检查词典是否缺失。
- 检查用户是否缺少城市信息。
- 看是否存在同名地址。

### 坐标不准

排查：

- 检查坐标系。
- 检查匹配等级。
- 对比 POI、AOI、门址结果。
- 看是否使用了中心点而不是入口点。

### 逆地理编码返回不符合用户感知

排查：

- 最近 POI 是否不合理。
- 点是否落在 AOI 内。
- 业务场景是否需要道路优先还是 POI 优先。
- 行政区边界是否有误差。

## 面试高频问题

### 问：地理编码的核心流程是什么？

答题思路：

- 地址清洗和标准化。
- 地址解析。
- 候选召回。
- 候选排序。
- 返回坐标、精度和置信度。
- 低置信度返回多候选或提示确认。

### 问：为什么地理编码要返回置信度？

答题思路：

- 地址可能不完整或有歧义。
- 多候选可能得分接近。
- 不同业务对准确率要求不同。
- 置信度可以帮助业务决定自动使用、人工确认还是拒绝。

### 问：逆地理编码为什么不能只取最近 POI？

答题思路：

- 最近 POI 不一定代表用户所在位置。
- 用户可能在小区、商场、道路、园区内部。
- 需要结合行政区、AOI、道路、门牌、POI 综合判断。

## 本节总结：面试突击记忆清单

- 地理编码是地址到坐标，逆地理编码是坐标到地址。
- 地理编码流程是清洗、解析、召回、排序、置信度。
- 地址结果要看精度等级，不能只看经纬度。
- 多候选和低置信度必须让业务感知。
- 逆地理编码要综合行政区、AOI、道路、门牌、POI。
- 对配送、导航、网约车等场景，入口点和可达点比中心点更重要。

如果面试突击时间有限，重点准备一个例子：用户输入一条模糊地址，系统如何解析并返回可靠坐标。
