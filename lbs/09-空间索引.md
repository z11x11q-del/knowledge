﻿# 09 空间索引

## 总览：空间索引解决“在大量地理对象里快速找相关对象”

空间索引是 LBS 后端必须掌握的基础技术。它解决的问题很直接：当系统里有几百万个 POI、几十万个围栏、海量道路和轨迹点时，如何快速查找某个位置附近的对象。

0 基础后端可以先类比普通数据库索引：普通索引用来加速按字段查询，空间索引用来加速按位置和区域查询。区别是空间查询不是简单的等值查询，而是“附近”“包含”“相交”“覆盖”等关系。

答辩中常见问题：

- 为什么附近搜索不能全表扫描。
- Geohash、H3、S2、R-Tree 是什么。
- 空间索引为什么通常需要二次过滤。
- 网格粒度怎么选择。
- 如何用空间索引支撑围栏和附近搜索。

## 分解一：为什么需要空间索引

假设数据库里有 1000 万个 POI，用户要查询 3 公里内的咖啡店。

如果逐个计算距离：

```text
1000 万个 POI * 每个计算一次距离
```

性能不可接受。

空间索引的思路是：

1. 先把空间划分成可快速检索的结构。
2. 查询时先召回用户附近的一小批候选。
3. 再对候选做精确距离或几何计算。

这叫“粗筛 + 精算”。

典型场景：

- 附近 POI 查询。
- 查询附近司机或骑手。
- 判断点可能命中哪些围栏。
- 查找定位点附近道路。
- 地图视野内点位加载。
- 热力图网格统计。

## 分解二：Geohash

Geohash 把经纬度编码成字符串。字符串前缀相同的位置通常距离较近。

例如：

```text
wx4g0ec1
wx4g0ec2
```

它们前缀相同，说明大概率在相近区域。

### 优点

- 实现简单。
- 字符串可作为索引字段。
- 适合附近搜索粗筛。
- 适合位置缓存和网格统计。

### 缺点

- 网格是矩形，边界附近要查邻居格子。
- 不同纬度下格子实际面积变化。
- 前缀相近不一定绝对空间连续。

### 使用方式

附近查询时：

1. 将用户坐标转成 Geohash。
2. 根据查询半径确定 Geohash 精度。
3. 查询当前格子和周边格子。
4. 对候选做精确距离过滤。

答辩重点：Geohash 适合粗召回，最终结果仍要算真实距离。

## 分解三：H3

H3 是 Uber 开源的全球六边形网格索引。

### 特点

- 使用六边形网格。
- 支持多层级分辨率。
- 邻接关系更均匀。
- 适合区域统计和供需分析。

### 适合场景

- 网约车供需热力。
- 城市订单分布。
- 运力调度。
- 区域覆盖分析。
- 轨迹流量统计。

### 为什么六边形有价值

六边形每个格子有 6 个邻居，距离关系更均匀，比方形网格在一些空间聚合场景中更自然。

后端答辩不要求深入 H3 内部实现，但要知道它是全球网格索引，适合空间聚合和分析。

## 分解四：S2

S2 是基于球面的空间索引系统。它把地球表面映射到立方体面，再进行层级划分。

### 特点

- 更适合球面建模。
- 支持层级 Cell。
- 适合大规模区域覆盖和分片。
- 可以把空间对象映射到一组 Cell。

### 适合场景

- 全球或全国范围空间服务。
- 区域覆盖。
- 空间分片。
- 附近查询。
- 大规模位置系统。

答辩答法：S2 和 H3 都属于全球离散网格系统，适合把连续地理空间离散化，便于索引、聚合和分布式计算。

## 分解五：R-Tree

R-Tree 是空间数据库中常见的索引结构。它用最小外接矩形（MBR）组织空间对象。

### 核心思想

每个空间对象都有一个外接矩形：

- 点的外接矩形就是点本身。
- 线的外接矩形包住整条线。
- 面的外接矩形包住整个面。

查询时先判断外接矩形是否相交，再做精确几何判断。

### 适合场景

- 查询某个范围内的 POI。
- 判断点可能落在哪些多边形内。
- 查询与路线相交的围栏。
- 查找附近道路。

常见实现：

- PostGIS GiST 索引。
- MySQL Spatial Index。
- SQLite RTree。

答辩重点：R-Tree 适合数据库空间查询，通常用于点、线、面范围和相交查询。

## 分解六：QuadTree

QuadTree 把二维空间递归四等分。

特点：

- 结构直观。
- 适合平面空间划分。
- 数据密集区域可以继续细分。
- 常用于地图渲染、碰撞检测、点位管理。

例如：

```text
整个城市
-> 四个区域
-> 热点区域继续四分
-> 直到点位数量可控
```

## 分解七：粗筛和精算

空间索引不能直接等于最终结果。

例如查询 3 公里内 POI：

1. Geohash 召回周边格子 POI。
2. 得到 500 个候选。
3. 对每个候选计算真实距离。
4. 过滤掉超过 3 公里的。
5. 按距离、热度、相关性排序。

例如判断点是否在围栏内：

1. R-Tree 查询外接矩形包含该点的围栏。
2. 得到 20 个候选围栏。
3. 对候选围栏做点在多边形内的精确判断。
4. 返回命中的围栏。

答辩要强调：空间索引主要做候选召回，精确结果还要几何计算。

## 后端开发视角：附近搜索索引怎么设计

### 数据入库

POI 入库时计算空间索引字段：

```text
poi_id
longitude
latitude
geohash_5
geohash_6
geohash_7
city_code
category
status
```

不同精度 Geohash 支持不同半径查询。

### 查询流程

1. 根据半径选择 Geohash 精度。
2. 找到中心格子和邻居格子。
3. 查询这些格子的 POI。
4. 根据类目、状态过滤。
5. 精确计算距离。
6. 排序返回。

### 性能关注

- 单个热点格子对象过多。
- 查询半径过大导致候选太多。
- 需要限制最大半径和返回数量。
- 热点区域需要缓存或更细粒度索引。
- 查询耗时要看 P95/P99。

## 答辩高频问题

### 问：空间索引为什么需要二次过滤？

答题思路：

- 索引通常是近似召回。
- 网格或外接矩形只能说明可能相关。
- 最终距离、包含、相交需要精确几何计算。

### 问：Geohash 边界问题是什么？

答题思路：

- 两个很近的点可能落在相邻格子，前缀不同。
- 查询附近对象时不能只查当前格子，还要查邻居格子。

### 问：如何选择网格粒度？

答题思路：

- 粒度太粗，候选太多，二次过滤慢。
- 粒度太细，索引数量多，范围查询要扫更多格子。
- 根据业务半径、数据密度、性能目标选择。

## 本节总结：答辩突击记忆清单

- 空间索引解决海量地理对象的快速召回。
- 常见索引有 Geohash、H3、S2、R-Tree、QuadTree。
- Geohash 简单适合附近搜索，H3/S2 适合网格聚合和大规模空间服务，R-Tree 适合数据库空间查询。
- 空间索引通常是粗筛，最终还要精确计算。
- 网格粒度要在召回量、精度和性能之间权衡。
- 附近搜索、围栏、地图匹配、热力统计都依赖空间索引。

如果只准备一个例子，就讲“如何查询用户 3 公里内的门店”，这是空间索引最容易讲清楚的答辩题。
